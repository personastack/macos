# PersonaStack for macOS specification

## Purpose

PersonaStack for macOS presents a selected PersonaStack web surface in a dedicated native macOS application window.

## Authority

- `my.personastack.ai` owns the hosted browser experience, cookies, public OAuth callbacks, and browser-facing composition.
- `personastack-api` owns identity, authorization, and product state.
- This client owns the macOS application bundle, WebKit configuration, native window behavior, local harness configuration through each CLI plugin manager, local Desktop Control executor and Cua lifecycle, per-user machine credential custody, authenticated outbound gateway connection, and installer packaging. It does not gain a second human login, workspace/persona authorization, integration/configuration store, or general product-state authority. The API is authoritative for device enrollment, selected configuration, current grants, and revocation. The gateway routes only currently authorized, finite requests to this installation.

## Version 0.1.0 behavior

- Start at the App URL in the saved three-service profile when present. Otherwise use the valid packaged `PersonaStackDefaultURL`; the one public installer defaults to `https://my.personastack.ai/user/personas`. `scripts/package-macos.sh` writes the release default through `PERSONASTACK_DEFAULT_URL`. An absent or invalid packaged value falls back to `http://127.0.0.1:8080/user/personas`.
- Accept `--personastack-url <http-or-https-url>` at startup for WebKit diagnostics. A custom diagnostic URL does not grant Gateway or MCP trust. The user must enter and save all three URLs through native Server Settings before native service credentials are used.
- Keep same-origin navigation in the app. Native bridges accept only registered main views at the exact active App origin, including scheme and port.
- Persist site data in the app's default WebKit data store.
- Keep navigation at the selected App origin in the app. Open user-activated links to other origins in the default browser.
- Keep `https://accounts.google.com` OAuth popups in a native child window so Google Sign-In can return to the embedded app.
- Allow automated top-level redirects to preserve existing OAuth callback flows.
- Download non-displayable responses to the user's Downloads directory.
- HTML file inputs in the main window and pop-outs open a native file picker attached to the requesting window. Honor the input's multiple-selection and directory-selection options. Cancel returns no files. Hosted image validation, cropping, uploads, and drag-and-drop remain owned by the web app.
- Expose no native JavaScript bridge, local API, credentials, or direct PersonaStack service connection.

## Version 0.1.3 behavior

- Request macOS notification permission when the application opens.
- Accept only the main-frame concern bridge payload `{ "version": "1", "event": "created" }` from the exact active App origin.
- Post a generic native notification when a new concern arrives while the app is running.
- Do not pass concern text, concern IDs, workspace IDs, user IDs, credentials, or other product data through the bridge.

- Clicking the app's Dock icon brings the main PersonaStack window forward, restores it when minimized, and reopens it when closed. A chat or stack pop-out must not replace the main window as the Dock reopen target. The menu bar's Open PersonaStack action uses the same behavior.

## Floating persona chat

- The hosted page detects the reply-capable `personastackChat` handler. Its existing Chat buttons open one ordinary native window per persona instead of the browser dock.
- Each window loads `/user/personas/chat/desktop-popout?persona_id=…` at the configured app origin. It shares the default WebKit data store. Native code never reads transcripts or calls chat APIs.
- A native, draggable dark title bar uses the standard macOS close and minimize buttons and a right-aligned Pin button. The native zoom button stays hidden. The hosted card meets the matching title bar with a square, borderless top edge. A matching fill behind its upper content removes transparent corner cutouts. A public layer mask keeps the lower chat-card corners transparent. Collapsing hides the bar, Pin button, and native buttons and resizes the same web view to a 72-point window containing a 64-point avatar.
- The native minimize button miniaturizes to the Dock. The sole Pin button sits in the top-right title bar and uses the hosted chat action's 28-point circular border and 14-point outlined pin. It toggles `.normal` and `.floating` for that window. The native chat web view hides hosted pin controls even on older hosted pages. Avatar click collapses or expands. Avatar/header drag also moves the window. Expansion preserves the expanded size at the avatar's current location and clamps to the screen.
- The native close button and Cmd-W use the hosted API-backed close flow. Failed closes keep the chat visible. Navigation errors, denied loads, login/logout navigation, and changed hosted presentation scope dispose stale windows. Same-scope main-page navigation preserves them.
- Main bridge messages have version `1`, action `sync` with an opaque hosted storage `scope`, or `open_persona_chat` with that scope and `persona_id`. Scope is an in-memory invalidation key, never an authorization source.
- Popout bridge messages use version `1` and only `minimize`, `close`, `collapse`, `expand`, `pin`, or `drag` with finite bounded `dx`/`dy` numbers. Reject extra keys, unregistered web views, child frames, and origins other than the configured app origin.
- Window geometry, pinning, and the persona-window map are ephemeral. No launch restoration, all-Spaces mode, native message storage, new authentication flow, or independent stream is added.
- Run focused native checks with `swift test --disable-xctest`. Tests use Swift Testing and in-process AppKit windows without network loads.
- Explicit hosted/native acceptance uses the sibling web repository: build its TypeScript assets, then run `node scripts/desktop-chat-fixture.mjs`. Set `PERSONASTACK_CHAT_FIXTURE_URL` to its printed loopback URL and run `swift test --disable-xctest --filter HostedChatSmokeTests` in this repository. The fixture uses fake messages. This lane is skipped by ordinary tests and never contacts the PersonaStack API.

## Stack pop-outs

- Only the desktop app exposes pop-out controls on Stack Settings. A strict main-frame `personastackStack` bridge accepts version `1` `open_stack_view` messages with one validated `stack_id` and either `graph` or `stream` view.
- Each view and stack pair has at most one ordinary, resizable, Dock-miniaturizable, visually borderless native window. It loads `/user/stacks/desktop-popout?stack_id=…&view=…` through the shared WebKit data store. Native code never reads stack content or calls PersonaStack APIs.
- The graph page and native canvas are transparent. The graph-only WebKit view disables its default opaque page fill so the OS remains visible between graph elements. It renders only the existing shared graph personas, integration circles, connection lines, and motion. The stream keeps its existing hosted card surface and stack-name heading against an opaque, edge-to-edge canvas.
- Stream windows hide the standard titlebar controls and use a narrow draggable native strip with a custom close button at the top-right. Do not add a window menu bar.
- Windows are ephemeral and close on login/logout invalidation, failed or denied hosted navigation, WebKit termination, or normal window close. They are not restored across app launches.

## Persona activity pop-out

- Only the macOS app exposes the pop-out control in the Persona Settings Live activity toolbar. It sends a strict version `1` `open_persona_activity` message with one validated `persona_id` through the registered main-frame `personastackStack` bridge.
- Open one ordinary native window per persona at `/user/personas/activity/desktop-popout?persona_id=…` in the shared WebKit data store. The authenticated hosted page subscribes to the existing authorized persona console stream and uses the same transcript renderer as Persona Settings.
- Keep the native titlebar controls hidden. Overlay the draggable native close control on the hosted Live Console title row, with no separate strip, title, or menu bar.
- Native code handles window presentation only. It never reads or relays persona activity data. Persona authorization and stream access remain owned by the hosted web/API path.
- Persona activity windows are ephemeral and close on session invalidation, failed or denied hosted navigation, WebKit termination, or normal window close.

## Native server settings

- The one public macOS installer defaults to `https://my.personastack.ai/user/personas`. Users can open **Server Settings…** from the menu bar or app menu, or press Command-Option-Shift-U.
- Store one complete App, Agent Gateway, and MCP base-URL record in local `UserDefaults`. The record contains no credentials. The production and LAN endpoint sets are predefined. A custom diagnostic URL never inherits production Gateway or MCP trust.
- Accept HTTP or HTTPS origins with optional trailing slash, non-default ports, IPv4, DNS names, and bracketed IPv6. Reject credentials, query strings, fragments, and non-root paths. HTTP traffic is unencrypted. HTTPS keeps normal certificate validation.
- `NSAllowsArbitraryLoads` is enabled because each operator-selected host is not known at package time and both WebKit and native URLSession must accept HTTP. This disables ATS policy for the app's network requests, including minimum TLS and forward-secrecy checks. HTTPS certificate trust evaluation remains enabled. Prefer HTTPS except for a controlled network that needs HTTP.
- A diagnostic `--personastack-url` remains the actual WebKit page URL while native Gateway/MCP features stay unavailable until the complete profile is saved. A corrupt saved profile loads only the local development fallback while Server Settings reports the corruption and permits repair.
- A saved record selects the main `/user/personas` page, the WebSocket Gateway path `/v1/desktop-control/ws`, and MCP `/v1/mcp`. An empty saved state uses the packaged default. Corrupt saved state keeps native settings available and uses the local development fallback until repaired.
- Save validates all three fields before it starts a switch. Switching fences Desktop Control, waits for any managed local harness file installation, invalidates old page replies and pop-outs, retires the old native bridge registrations, persists the record, and creates a fresh WebView at the selected App URL. It does not copy cookies or credentials across origins, revoke an old environment's enrollment, or retarget a local CLI installation.
- Keychain enrollment credentials and Desktop Control relay preferences are scoped to the full normalized three-URL profile, including when profiles share an App origin. Gateway and MCP trust must match the selected derived endpoints, including scheme and port. A new profile starts with remote control disabled.
- Native authenticated enrollment and Gateway requests reject redirects. Before writing a bearer-bearing local MCP plugin, the app makes an unauthenticated `HEAD` request to the exact selected MCP endpoint and rejects a redirect from that preflight request. This preflight does not control redirect behavior for later authenticated requests made by Codex or Claude Code; those clients own their HTTP redirect behavior. Normal HTTPS certificate validation remains enabled.
- The website, API, and native service deployments keep their existing ownership. No server discovery API, second installer, LAN download artifact, or website environment selector is added.

## Automatic updates

- DMG and Homebrew builds use the same Sparkle 2 updater and signed appcast at `https://raw.githubusercontent.com/personastack/homebrew-tap/main/appcast.xml`. Release bundles pin the public Ed25519 key, require signed feeds, verify archives before extraction, disable anonymous profiling and release-note JavaScript, and keep signed-feed failures from expiring.
- Sparkle owns daily update checks, downloads, verification, staging, replacement, and relaunch. Its automatic download preference is the only stored copy of that preference. It defaults off. Enabling it permits background download and installation on normal quit, never a forced restart.
- The native app menu and menu-bar dropdown expose **Check for Updates…** and the automatic-download setting. Update checks start only after application launch and only when the packaged public key and fixed HTTPS feed are valid.
- Background update discovery suppresses Sparkle's scheduled alert and shows a once-per-version in-app toast when the main window is visible or a native notification when it is not. The user can reopen the existing Sparkle confirmation from either reminder. Automatic downloads show their background state without offering an action that starts a competing update check. If Sparkle falls back to scheduled UI for authorization or another required user action, PersonaStack switches to **Continue Update…** and reopens the existing session. Information-only updates remain on a **View Update Information…** path. A single app-lifetime notification delegate routes download and restart actions while preserving concern notifications. Denying notification permission leaves menu actions available.
- Sparkle's progress driver remains visible during download and preparation. The menu projects checking, download percentage, extraction percentage, and ready state. Restart Now uses Sparkle's immediate-install relaunch handler for prepared automatic updates. Manual update confirmation uses Sparkle's install choice. Both paths run normal app termination so Desktop Control shutdown runs. Foreground update restarts reopen the main window and resume the saved Desktop Control relay. A success status appears only after the target bundle version launches.
- When the bundle is on a read-only volume or under App Translocation, PersonaStack does not initialize Sparkle. It performs no update checks, downloads, or install-on-quit attempts. The Updates menu explains how to move PersonaStack into Applications. The saved automatic-download preference remains unchanged and resumes when the user opens the Applications copy. Success remains version-verified, so a failed replacement is not reported as complete.
- Choosing **Skip This Version** in Sparkle clears PersonaStack's matching offer, ready action, notification, and restart metadata. Dismissing the installing-stage confirmation keeps the prepared update ready for ordinary quit or a later restart.
- Release packaging requires a stable numeric `major.minor.patch` version and writes the same value to `CFBundleVersion` and `CFBundleShortVersionString`. The package embeds Sparkle's universal framework and helpers. Release automation publishes the immutable DMG and versioned tap artifact before regenerating and publishing the signed appcast.
- The Homebrew cask enables `auto_updates` beginning with the first updater-enabled release. Previous app versions without Sparkle require one normal Homebrew or DMG update to bootstrap the updater.
- App replacement preserves the default WebKit data store, local user preferences, Keychain services, and normal Desktop Control startup. It does not replay in-memory tasks or drafts.

## Local persona sessions

- Only registered main application web views expose the reply-capable `personastackLocalSession` bridge. Validate exact configured origin, scheme, port, and main frame. Floating chats and OAuth popups cannot launch sessions.
- Version `1` request messages are `state`, `select_harness`, `prepare`, and `configure`. The `state` reply reports capability version `2` when native Configure is supported. Older version `1` replies identify clients that must be updated before preparation. Reject unknown fields. All messages carry the hosted presentation scope. Preparation checks the installed CLI before returning a native pending UUID. Pending IDs bind persona and harness for five minutes and are consumed once. Scope changes and login/logout invalidate pending work.
- Support only installed Codex CLI and Claude Code. Probe the user's login shell with bounded output and time. Require at least the inspected Codex 0.154.0 or Claude Code 2.1.152 baseline and required plugin-manager commands. Missing or unsupported CLIs require user installation or update. Never run an installer or obtain provider credentials.
- Keep one native harness preference per app origin. `select_harness` persists that preference without preparing or configuring a harness. Never persist bearer tokens or local-harness bundles in preferences. The hosted app remains responsible for the later authenticated configuration-preparation POST. The API owns each independent fixed 365-day credential and its ongoing authorization.
- Validate the typed local-harness bundle, fixed lifetime, selected profile's exact MCP endpoint, artifact digest, aggregate limits, and safe paths before local writes. Production and LAN profiles use their configured MCP endpoints. A custom profile is accepted only after all three service URLs are explicitly selected and saved; its bundle must match that profile's exact MCP endpoint, including scheme, host, and port.
- Private desktop plugin sources live under `~/Library/Application Support/PersonaStack/LocalHarnessPlugins/<harness>/<profile-hash>/<UUID>` with mode 0700. Files use 0600. An ownership manifest and source digest record the active source for that harness profile. Reconfiguration validates the recorded source, registered marketplace, installed plugin identity, and cache permissions before it removes only the recorded PersonaStack plugin and marketplace. Refuse symlink traversal, unmanaged collisions, and modified owned content.
- Each source is a local marketplace with one `personastack-local-<profile-hash>` plugin and `personastack-desktop-<profile-hash>` marketplace. Codex uses `.agents/plugins/marketplace.json`, `.codex-plugin/plugin.json`, and its `mcpServers` manifest shape. Claude Code uses `.claude-plugin/marketplace.json`, `.claude-plugin/plugin.json`, and its direct server-map manifest shape. Both receive a private authenticated MCP entry, the eager `PersonaStack` skill, and namespaced selected-skill snapshots that preserve relative assets and metadata. After install or retry, Desktop makes the verified managed cache owner-only. Path aliases are accepted only when they identify the same source directory. Cache permissions change only after plugin identity and full source contents match.
- Configuration runs only bounded selected-CLI plugin-manager commands with the existing profile directory. It never opens Terminal or starts an interactive CLI harness. It never edits `AGENTS.md`, `CLAUDE.md`, shell profiles, raw CLI configuration, or profile symlinks. Existing CLI auth, profiles, model settings, MCP servers, hooks, and plugins remain user-owned.
- Local-session diagnostics use the `ai.personastack.desktop` OSLog subsystem and `local-session` category. Record only allowlisted action names, fixed stage names, and finite error codes. Never log request bodies, scope, persona/workspace identifiers, pending IDs, bundle fields, bearer credentials, paths, CLI command output, or unrecognized input values. Read recent events with `/usr/bin/log show --last 10m --style compact --predicate 'subsystem == "ai.personastack.desktop" AND category == "local-session"'`.
- This is not a sandbox. Downloaded private skills and persona instructions remain on the Mac. Existing CLI tools and plugins retain their user's trust. Fakes do not prove live CLI authentication or provider/MCP connectivity. Those require separately authorized smoke tests.

## Installer distribution

Each semantic version is an unsigned universal macOS disk image with a branded Finder background, a drag arrow, and an Applications shortcut. Users install by dragging `PersonaStack.app` onto `Applications`. A public GitHub release retains the immutable `PersonaStack-<version>-unsigned.dmg` installer. The release workflow copies the same DMG into a versioned public `personastack/homebrew-tap` Git tag and updates the `personastack` cask. Homebrew installs it with `brew install --cask personastack/tap/personastack`.

For local package validation, `scripts/package-macos.sh` accepts `PERSONASTACK_CODESIGN_IDENTITY`. A named keychain identity signs the app bundle and verifies it before image creation. `-` performs an ad-hoc signature experiment and gives the artifact an `adhoc` suffix. Ad-hoc identity is not proof of stable TCC attribution, Login Item approval, or a distributable signed build. The public release workflow remains unsigned until its signing and notarization credentials are configured.

## Desktop Control relay

- On the first launch of an installed app copy, register Launch at Login automatically through `SMAppService.mainApp`. Record the attempt once per macOS user. Later launches preserve a user disabling the login item. Existing enabled or approval-pending registrations are not registered again. Read-only disk images, App Translocation, and development executables do not consume this first-launch attempt. Registration failures and macOS approval requirements appear in the existing menu error area. The Launch at Login action remains available for a manual retry.
- A desktop-only hosted CTA starts a strict main-frame native setup bridge. It validates the configured app origin and frame, accepts only typed setup/status actions, rejects unknown fields, and never treats a workspace, installation ID, `ready` flag, path, shell command, or URL from JavaScript as authorization.
- Each installation can connect to one PersonaStack account and one integration configuration at a time. The Keychain identity is independent of app version. An explicit setup first stops local control and revokes the saved installation, then attaches the fresh authenticated setup ticket with the Keychain machine credential. The API removes the prior integration and persona bindings before the new runtime is started. Disabling a config still reserves the installation until explicit setup or owner removal. Replacement preserves the saved installation ID and credential.
- The API authorizes a selected workspace and issues short-lived setup material. Native exchanges it directly with the gateway/API device authority. Machine credentials live only in Keychain and native network/process memory. They never enter WebKit, local storage, prompt text, MCP arguments/results, logs, or command environments.
- Desktop Control Keychain accounts and relay preferences are keyed by the full normalized App, Agent Gateway, and MCP base-URL profile. Enrollment binds the selected App origin and Gateway URL into the saved installation. Every credentialed enrollment request checks that binding before sending credentials. Gateway and MCP requests must match the selected profile's exact derived endpoints, including scheme, host, and port. Custom profiles are supported only through their explicitly selected endpoints. The retired `my.personastack.lan` origin is denied. Legacy origin-scoped and unscoped `installation` items migrate only into an exact built-in Production or LAN profile, with any saved origin and the Gateway required to match that profile; a legacy item for another environment is ignored. The new profile-scoped item is saved before use, and disconnect retains the stable installation identity and credential in Keychain after remote revocation. An explicit setup with the retained Keychain machine credential and a fresh human-authorized setup ticket replaces the prior integration, then reuses the same stable installation identity. The installation ID is a locator, not a deletion token. Pending setup has a native page generation that cancellation, workspace changes, and navigation invalidate before deferred credential, login, or relay commits.
- Persisted relay enablement follows API-owned registrations. Setup cancellation, startup or manual resume, reconnect, and successful config revocation query `/v1/desktop-control/ready` with `validate_only` and `relay_state_only`. The API returns `has_config` for the installation reservation and `has_active_config` for enabled remote access. A disabled configuration still reserves the installation across every account and workspace. A false result stops the Gateway, local control resources, and any Cua service process started by this PersonaStack app instance. It clears relay preferences only after local cleanup succeeds, while retaining the Keychain installation credential and Cua install. A pre-existing Cua process is left running. Failed local cleanup keeps the Gateway and reconnect path available for a revocation retry. A true active result preserves the enabled installation connection. If the read fails, native keeps the relay so a transient API error cannot disconnect the enabled integration. Initial setup may start before a config exists and performs this check when setup ends.
- The Desktop Control page's native `state` action returns local installation presence, API-owned `configuration_in_use`, Cua readiness, executor readiness, Gateway connectivity, and paused state. The reservation field distinguishes an unconfigured installation from one linked outside the current workspace. The web page compares the installation locator only with configuration lists in the viewer's API-authorized workspace directory; foreign account and inaccessible workspace details stay private. Resolving or reopening the page never replaces a link. The page first renders API-owned config status, then runs the aggregate idle check and reads this local snapshot asynchronously. This local status does not select, expose, or mutate another user's configuration.
- Removing a Desktop Control mapping in the hosted page first revokes that exact user/workspace/config. After success, the native page bridge runs the aggregate idle check. It stops the Gateway/Cua services when the API reports no enabled configuration for the installation. If the aggregate read fails, native preserves the relay and the page reports that local stop is not confirmed. Scoped Gateway revocation closes that mapping's lease, file handles, and managed process groups.
- Desktop Control stays available in a per-user background/menu-bar application while enabled. Closing ordinary windows does not stop it. A relay-started app uses the accessory activation policy so login startup stays in the menu bar; the menu's Open PersonaStack action restores the regular app policy and fronts the existing main window, including one SwiftUI left offscreen at startup, or opens it if absent. The menu bar shows connection, GUI/filesystem/process readiness, pause/resume, repair, open-app, and disconnect. Startup Keychain failures appear in the menu with a direct retry, and a missing enrollment directs the user back to setup. An idle relay with no active configuration must not show as enabled after a manual start. Pause refuses new control while retaining a paused heartbeat; disconnect pauses locally, revokes the installation with its machine credential, and stops the gateway connection. It retains the Keychain identity so disconnect cannot create a new installation while the old integration remains. Reservation reads work for the revoked installation. Reactivation requires explicit setup with machine proof and a fresh authenticated setup ticket; attachment removes the prior integration and persona bindings. Browser logout does not disconnect the durable installation. Explicit replacement setup stops local control, revokes and fences the old session, then asks the API to remove the prior configuration before creating a new link. The stable installation ID and machine credential stay in Keychain. Other installations remain untouched. If Keychain proof is missing, native must not authorize deletion from the installation ID; the signed-in owner selects and removes the prior config through normal workspace authorization before enrolling a replacement.
- The app installs or repairs only the pinned Cua Driver release through a reviewed, integrity-checked artifact. Prefer reuse of a compatible, healthy `CuaDriver.app`; do not silently replace an unmanaged install or run Cua's mutable latest installer. Permission grants belong to the signed `com.trycua.driver` app. Launch the app bundle through LaunchServices with the documented `serve` argument, without activating it, then proxy the pinned `cua-driver mcp` contract. Preserve Cua's MIT license notice beside the managed payload even when the pinned universal archive includes a `LICENSE` file. Cua documents macOS 14 (Sonoma) or later. Its telemetry defaults on, so PersonaStack disables telemetry and automatic update checks through process-scoped settings without mutating shared Cua preferences. If a compatible Cua process is already running, its telemetry settings remain externally controlled and PersonaStack never terminates it. Repair preserves the user's prior paused state. Setup retries Cua startup once with a forced managed install and probe after normal startup fails. Manual repair uses the same single retry. The installer replaces only a matching PersonaStack-owned install. The native runtime commits a fresh or replacement install only after checking lifecycle generation and confirming no Cua process is running in the same main-thread operation as the filesystem mutation. If Cua is running, repair stops and asks the user to quit it first. Lifecycle generations fence setup, repair, enrollment, credential commit, and reconnect attempts from newer pause, resume, or disconnect operations. A single pending Gateway attempt owns the socket handoff; command dispatch and disconnect callbacks are bound to the current connection; readiness failures cannot overwrite a later attempt. A readiness failure keeps a generation-fenced Gateway reconnect loop active even when its first connection attempt fails. Disconnect uses the configured PersonaStack service origin for revocation. It sets local and Gateway readiness to paused before stopping sockets and local processes. If remote revocation fails, local control remains paused and the authenticated connection stays available for heartbeat and reconnect while the user retries disconnect. Pause and disconnect stop a pending Cua MCP proxy before its readiness probe can continue. Validate daemon generation, version, tool schemas, real screenshot and accessibility state, and permission readiness before claiming GUI ready. Cua release v0.29.1 uses a repository-wide GitHub prerelease label to manage independent product releases; its own notes identify it as stable SemVer and publish the universal macOS archive checksum.
- The native Cua MCP proxy starts one `cua-driver mcp` process against an explicit per-user socket. LaunchServices starts the selected signed app with `serve --socket` for that same path. Before setup or GUI work, the runtime checks that the kernel socket peer PID belongs to the selected app bundle. A missing socket, changed owner, or different app fails closed. The proxy uses the pinned CLI's `--embedded` client option to suppress its automatic app launch if the socket is absent; the signed standalone daemon still owns the macOS permission identity. Permission readiness calls use `check_permissions` with `prompt=false`; Cua refuses OS prompt requests through MCP, so the signed Cua app and macOS System Settings own permission grants. The proxy performs MCP initialization, reads a bounded newline-delimited JSON-RPC response stream, checks the required tool catalog, and permits calls only to PersonaStack's reviewed tool-name allowlist. Its child process receives only the normal user environment allowlist. Timeout or protocol failure stops the proxy without replaying a tool call. If a GUI command leaves the proxy unable to pass its permission probe, the runtime starts a fresh embedded proxy against the same PID-verified daemon, validates the catalog and GUI readiness, and swaps proxies only after success. A failed GUI command is never replayed automatically. Degraded heartbeats can repeat this proxy recovery without reinstalling or stopping the Cua daemon.
- One authenticated outbound connection per installation serves one integration configuration in one account and workspace. The API owns current workspace/persona authorization. Gateway owns connection routing. Every frame carries current installation generation, authorized configuration/workspace/persona scope, operation, request identity, and deadline. Connection credentials alone do not grant a desktop action.
- API/MCP dispatch invokes Cua GUI operations or the native filesystem/process executor according to a finite tool schema. Do not proxy arbitrary local MCP catalogs. Do not invoke file operations through shell strings. Native file and process actions execute as the logged-in user and follow that process's macOS permissions.
- The native executor supports bounded file list/search/stat/open/ranged read/write/patch/move/create/remove, and managed shell processes with separate stdout/stderr pipes, stdin, output cursors, status, deadline, and cancellation. Text file results include bounded UTF-8 content plus byte and line metadata; byte-page boundaries preserve complete UTF-8 characters. Binary results include MIME/encoding hints and base64 bytes. `file_open` returns descriptor size, modification time, and a size/mtime revision token. It returns image content for supported images up to 5 MiB by reading bounded chunks, keeping the encoded MCP result within the shared 8 MiB frame bound. Search combines filename and content matches with OR semantics and includes line numbers for content matches even when the filename also matches. It returns an expiring continuation token when a page stops at its result/time bound and identifies files whose 4 MiB content scan was truncated. Line-range reads that stop mid-line mark truncation and leave `next_line` on that partial line. Symlink metadata includes the resolved target. Stat, list, search, and remove preserve macOS permission denials as the actionable `desktop_file_permission_denied` response. It may offer PTY mode as a finite option. File, search, and execution handles are ephemeral, owner/config/session scoped, and reauthorized on every call. No pod mount, transparent path translation, durable command queue, or output archive is created.
- Native file errors use bounded MCP codes. Permission denial names PersonaStack Desktop and points back to access available to the logged-in macOS account. Expired handles, invalid ranges, handle limits, changed files, and incomplete searches have separate recovery guidance. A failed append, create, or offset write reports an uncertain write outcome and asks the caller to read the file before retrying.
- Shell execution uses a native process-group supervisor that waits for ordinary shell background jobs and retains its leader through cancellation escalation. Stdin uses bounded nonblocking writes so cancellation and cleanup can stop queued writers even if a detached process retains the pipe. Shell termination cancels pending stdin writes. Closing stdin fences later writes before queuing EOF, and completed-session pruning retains any session with pending stdin operations until its queue drains. Cancellation checks whether the owned process group still exists after the leader exits, sends KILL to remaining group members, and reports cleanup failure if the group remains. A process-group id cannot be reused while members remain in that group. Arbitrary shell text can deliberately detach a process or exit before the supervisor's wait. Such work may outlive its shell execution and cannot be canceled after the process group ends. If it keeps an output pipe open, the executor drains it for at most two seconds, closes the reader, and marks the output cursor as having a gap. This is user-level shell execution, not an OS sandbox or a guarantee to clean up every descendant.
- Process output streams from the native app over the current gateway request to MCP. Output frames are bounded, ordered per process, and isolated to the authorized reader. They do not use generic session broadcasts. MCP may send request-scoped progress notifications to a capable client and returns bounded output/cursor state for subsequent reads and input. Do not promise live model display unless the actual worker/runtime MCP client proves it. A command can continue across one completed tool request while its explicit bounded execution remains authorized.
- One local control session owns the shared screen, clipboard, files, and commands at a time for the installation. The native executor owns process and file handles only for that control owner. Config revocation is scoped to installation/workspace/config and its config-version fence. Matching config or binding revocations join direct, release, or expiry cleanup and acknowledge only after callbacks, file handles, and managed processes finish cleanup. Unconfirmed cleanup stays fenced; a same-scope retry repeats it and only a successful retry restores availability when cleanup caused the unavailable state. Revocation must not affect resources outside its configuration scope. The executor rejects command admission during bounded cleanup, so a replacement configuration cannot acquire resources while the old handles close. The gateway reader caps concurrent command tasks at 32 and reserves one task slot for revocation. Pause, ownership expiry, disconnect, and app termination close handles and settle managed process groups where possible. A shell that deliberately detaches work may leave user processes running after its execution ends. Do not claim an OS sandbox, isolation among workspaces, or undo of completed actions.
- Desktop Control observes `com.apple.screenIsLocked` and `com.apple.screenIsUnlocked` through the public distributed notification center, and `NSWorkspace.willSleepNotification` through the public workspace notification center. These macOS system signals still require packaged delivery acceptance. No private lock-state query is used. Startup lock state is unknown. Foreground setup may resolve that state only after native user confirmation; background relay startup refuses control until an unlock notification is observed. Screen lock and impending sleep synchronously fence new work and interrupt the owned Cua MCP proxy before any Gateway heartbeat send; native cleanup then closes file and shell resources. Wake alone does not restore control. Results from commands that finish after lock are rejected. A Cua action already dispatched inside its standalone daemon may still finish and needs packaged acceptance. Unlock must pass a nonprompting Cua readiness probe before publishing ready.
- Persona unbinding uses `desktop_control_revoke_binding` with installation/workspace/config/persona, empty run ID, positive config version, and the revoked binding generation cutoff. Ordinary commands carry the authoritative binding generation in the target generation field. The native executor remembers the highest cutoff per scoped persona binding, denies commands at or below it, and cleans only a matching lease at or below that cutoff. A delayed revocation cannot stop a newer rebound lease or revoke a shared config from other personas. Binding revocation uses the reserved Gateway command slot and is accepted while control is paused or locked.
- Socket loss fences the current native executor immediately. It releases the lease, closes file handles, and settles managed shell process groups before a fresh executor may accept work. Unconfirmed cleanup leaves remote execution unavailable. Lease cleanup rejects concurrent acquisition and fences results from old lease epochs. Running managed commands refresh the 90-second idle lease on the five-second maintenance tick. The 30-minute hard lease lifetime still expires, and each command timeout is capped by the lease's remaining hard lifetime.
- GUI, filesystem, and process readiness are distinct. Cua permission denial does not imply native filesystem denial, and vice versa. Cua-only readiness errors block GUI commands while local file and shell commands remain available when the native executor is healthy. The setup bridge reports `cua_ready` and `native_executor_ready` separately. Heartbeat absence determines offline state. Permission or executor failure is actionable readiness state, not machine absence.
- `desktop_control_status` remains callable when the current installation is paused, the session is locked or awaiting its first unlock, GUI permissions need attention, or native cleanup has failed. After normal API configuration and persona-binding authorization, it reports connection, GUI readiness, native executor readiness, pause, locked and unlocked session state, control availability, and exclusive-lease occupancy. A healthy native executor stays distinct from pause or lock state.
- Gateway heartbeats report `ready`, `permission_required`, `cua_unavailable`, `paused`, `locked`, or `upgrade_required` as runtime health changes are known. Heartbeat construction checks the embedded Cua MCP child as well as the signed daemon before reporting `ready`. When the child exits, the relay reports `cua_unavailable`, closes the dead child, and attempts bounded replacement through the existing readiness probe. Normal ready-state heartbeats use cached permission readiness. Degraded recovery performs a bounded functional probe before reporting `ready` again. A GUI command failure, including an MCP tool result marked `isError`, rechecks Cua permissions without prompting, updates cached readiness, and publishes the result on the next heartbeat. A structured Cua permission result with a denied grant maps to `permission_required`; a Cua tool or RPC error without structured grant flags maps to `cua_unavailable`. The setup shell probe requires streamed output across stdin barriers and a zero exit code before enrollment. An unsupported Gateway protocol or a typed `upgrade_required` failure sets the local readiness to `upgrade_required` and tells the user to update PersonaStack Desktop. Protocol upgrade does not delete or replace the enrolled installation credential. A Cua permission or startup-probe failure on an already enrolled Mac keeps the authenticated connection alive and reports its finite GUI readiness state. The native executor reports its own unavailability on file and shell calls without marking the machine offline.
- After a transient Cua error, the relay retries one read-only observation if its permission check or proxy repair restores readiness and the same connection, lease, and unlocked session remain valid. Input, application, window, clipboard, and browser actions are never replayed after an uncertain outcome.
- Native process failures return finite tool errors for denied working-directory access, invalid working directories, process limits, expired execution handles, invalid input, unconfirmed cancellation, and command startup failure. These per-call errors do not change machine connectivity or imply that filesystem or Cua GUI permissions are broken.
