# Locked-session grant candidate

The implementation follows Apple's [Authorization Plug-in interface](https://developer.apple.com/documentation/security/extending-authorization-services-with-plug-ins). The inspected open-source examples were [XCreds](https://github.com/twocanoes/xcreds), [NoMAD Login](https://github.com/jamf/NoMADLogin-AD), and [authchanger](https://github.com/jamf/authchanger). The display adapter uses public CoreGraphics transfer tables. [RustDesk's macOS source](https://github.com/rustdesk/rustdesk/blob/master/src/platform/macos.mm) demonstrates this approach. No upstream implementation was copied.

`build.sh OUTPUT_DIRECTORY` builds and tests the candidate without installing it. It also writes a portable offline policy composer and `candidate-right.plist`. The leaf uses the privileged mechanism and one attempt. The composer adds a separate any-of branch before the original screensaver delegates. A denied candidate retains those delegates in their original order. Existing multi-delegate all-of policies are rejected. Removal preserves unrelated later policy changes. These generated files are review artifacts. The script never runs `security authorizationdb`.

`Sources/PersonaStackCore/DesktopLockedControlGrantBroker.swift` contains an in-memory one-shot grant state machine. `Sources/PersonaStackCore/DesktopLockedControlGrantIPCServer.swift` and the separately built C plug-in contain a fixed-size local socket path. The native supervisor now composes the grant broker, local socket, lock coordinator, display privacy, and local takeover handling. A separate authenticated app-to-supervisor channel carries the existing lease scope. The normal runtime conditionally activates these components after installed-policy verification and explicit local acknowledgement. The component has not been installed into this working Mac's screensaver policy.

The candidate grant binds one gateway connection, one existing control lease token, one console UID and audit session ID, and a monotonic expiry. The controller can arm one grant. An authorization mechanism can consume it once after a role-specific peer verifier approves its OS peer credentials. The app checks the peer audit token against Apple’s code-signing requirement for `com.apple.authorizationhost`, root effective UID, and the app’s active audit session. The plug-in checks the server audit token against the exact release certificate in `Resources/ReleaseSigningCertificate.der`, the current console UID, and its own audit session. Consumption happens before the mechanism may return Allow. Every mismatch, expired grant, duplicate consume, or untrusted peer denies.

Revocation before consumption removes the grant synchronously. No later request can consume it. Revocation after consumption returns `awaitingOSLock` and keeps the consumed grant fenced. While the grant is armed or the authorization transition is pending, `mayStillUnlock` stays true. An initial locked snapshot cannot settle the permit because an Allow may still be in flight. Only the controller may clear the fence after first observing the actual unlocked console session and then reading back that same session as locked. A caller must keep privacy protection in place while either observation is pending or unavailable.

## Qualification boundary

The library does not treat PID, UID, a signing identifier, or a team identifier supplied by a caller as authentication. The IPC adapter obtains its host identity from the local socket audit token and `SecCodeCopyGuestWithAttributes`. The authorization host is shared by mechanisms. This check authenticates the Apple host process. It does not identify the specific loaded plug-in module. This Mac’s current authorization host has been verified read-only as Apple-signed `com.apple.authorizationhost`; other OS builds still require the same check.

Apple documents `SetResult` as the decision for the current mechanism. The engine may continue through later mechanisms. `DidDeactivate` acknowledges mechanism deactivation during interruption. Neither callback reports completion of the full screensaver authorization to the app. `mayStillUnlock` stays true until either pre-consumption revocation succeeds or the app observes the actual unlocked console. The native coordinator must then observe that same session relock before restoring displays. If it cannot observe the expected state, it must retain privacy and require local manual recovery. The current audit-session match has source coverage but still needs a dedicated-Mac authorization-host trial.

The authorization plug-in in `Experiments/LockedSessionProbe` remains deny-only. The candidate build script adds no installer or policy mutation. The separate explicit package path now provides a one-shot native policy writer. It adds no resident privileged daemon. `build.sh` creates only a separate candidate bundle in a caller-specified output directory, runs deterministic callback tests without opening sockets, and refuses to replace an existing candidate. Any installed bundle and its socket-owning controller must be root-owned and read-only. A long-lived supervisor must own display privacy so app exit cannot restore gamma while an authorization transition remains pending. Any future screensaver rule must retain the original system authentication mechanism as a fallback. The candidate must not replace the system screensaver right with a standalone grant mechanism. The candidate must not be installed or enabled in system policy until the signed build, audit-session match, and real locked-session flow pass dedicated-Mac qualification.


## Installed-policy evidence

The native setup verifier reads the owned right and current screensaver rule. It also requires `/Library/Application Support/PersonaStack/LockedControlPolicyBaseline.plist`. The receipt records version `1`, the owned `right`, and `manualFallbacks` in their original order. Its file and every parent must be root-owned with no group or other write access and no symlinks. Normal root-owned directory mode 0755 and file mode 0644 are supported.

Generate the receipt offline from the same original policy used for composition:

```sh
python3 policy.py receipt screensaver-before.plist LockedControlPolicyBaseline.plist
```

The command refuses existing output files. It does not install the receipt or change authorization policy. The explicit package installer re-reads the current policy before applying the reviewed composition and installing the matching receipt. The native writer and verifier share `DesktopLockedControlPolicy` in Core. The Python composer remains an offline review artifact. A receipt generated from a stale or already modified policy is not installation evidence. The verifier requires exactly the recorded manual delegates after the owned branch. Later unrelated policy changes remain untouched but do not qualify without review. A separate native acknowledgement is required before the existing full-control setting gains locked-session authority. Opening diagnostics or the checklist does not record acknowledgement.

## Explicit installer package

`scripts/package-locked-control.sh` builds the internal pinned Developer ID plug-in and `PersonaStackLockedControlInstaller` component. `scripts/package-desktop-installer.sh` combines this component with the app in the main PersonaStack package. The app no longer contains or opens a separate helper installer. Apple's Installer owns elevation. The fixed payload tool verifies root ownership, protected paths and signatures before using Authorization Services. It takes no policy or path arguments. It reads the current screensaver rule, preserves its manual delegates, writes the baseline and inert leaf, checks for policy drift, applies its branch and verifies readback. Repeated setup of a matching installation is a no-op. Conflicting state fails without replacing the baseline.

The package is not installed by building it, launching the app or opening diagnostics. The native Finish flow opens its bundled package only after the user's explicit Install action. Finish remains incomplete until verified readback and explicit acknowledgement. Public release builds require Developer ID Installer signing as well as the signed payload and normal notarization gates. No physical qualification is implied by this source path.

A matching inert receipt and private leaf permit an explicit retry. A malformed or truncated receipt is conflicting state and requires review. The installer never overwrites that evidence. It does not promise recovery from a crash during receipt writing.
