## OpenClaw dispatch agent

Native discovery reads configured `agents.entries` or the supported `agents.list` shape from the selected profile. A sole agent is selected automatically. Several agents require the native picker. A config with neither roster property exposes the pinned upstream implicit `main` agent. Explicit empty, invalid or ambiguous rosters never fall back to `main`. The selected opaque candidate binds the physical profile and config snapshot. Preparation and enrollment reject stale choices before exchange or persistence. The helper stores the exact selected agent and validates its presence before configuration, effective catalog checks and dispatch. The API continues to select the physical profile. Agents do not create separate persona targets. [OpenClaw agent configuration](https://docs.openclaw.ai/gateway/config-agents)

## Pinned source evidence

Read directly from the identified immutable Git revisions. These are source contract evidence. No installed-runtime or signed-app interoperability is claimed.

Hermes `/v1/runs` does not consume a `conversation` body field. Its supported declared-conversation owner is `X-Hermes-Session-Key`. The helper hashes the exact API conversation ID and issued MCP namespace into this bounded header. It omits `session_id` for those assignments because an explicit native session overrides the header. Hermes resolves and binds its own current transcript. Assignments without an API conversation keep the existing per-run session fallback. The API remains the durable conversation and composed-prompt owner. The existing assignment ID is sent as `Idempotency-Key`.

Native config parsing currently supports strict JSON only. Pinned upstream OpenClaw also supports JSON5 through its config reader. ## OpenClaw MCP Apps and no-model readiness

The supported path uses the pinned Gateway's MCP Apps capability. Native setup asks for per-profile Apps approval separately from gateway start or restart approval. The private Repair receipt also pins the exact observed connection generation and API target-selection revision. Ordinary installation, ConfigRefresh and Check cannot grant Apps permission. A missing flag returns `mcp_apps_disabled`, including when the selected gateway is stopped.

Apps approval changes only the selected profile's `mcp.apps.enabled` value and its exactly owned PersonaStack MCP entry. It preserves other keys. The helper accepts the upstream default bind or explicit `gateway.bind: "loopback"`. It refuses lan, custom, auto and malformed settings before writing. A running gateway must also prove that every selected-port listener address is numeric loopback on the same attributed PID. CLI bind overrides cannot substitute a matching config/profile for this evidence. When the configured port is unused, a bounded current-user listener scan must also exclude the selected physical profile on another CLI-overridden port. Distinct sibling profiles remain available. Helper-started gateways explicitly pass `--bind loopback` because the native default can depend on the launch environment. Apps enables HTML App capabilities. The pinned upstream starts an additional local sandbox listener when Apps is enabled. That listener inherits Gateway bind hosts. Existing sandbox settings stay unchanged. A configured non-loopback bind must be changed through the native runtime owner. Stopping it alone cannot make Repair enable Apps. The Apps flag stays enabled after disconnect as a user-selected profile feature. Config reload may require a selected gateway restart. A profile with reload disabled requires a manual selected-gateway restart before discovery can succeed.

Consented Repair retains a bounded pending setup flag in the existing binding. The normal reconciler completes it after the scoped gateway is available. It calls `sessions.create` with an explicit helper-owned key, selected agent and idempotency key. It omits message, task, attachments, title source and model overrides. The returned `runStarted` must be false. It then calls `mcp.app.discover`, reads `sessions.describe`, checks `tools.effective` and reads the same metadata again. Generation, target, admission and configuration checks guard saving the returned session key, ID and optional lifecycle revision. No model run is used for readiness.

Ordinary Check uses the retained session identity. It only reads metadata and effective tools after selected-profile authentication and process ownership checks. A reset identity, foreign agent, denied tool or cold/stale catalog prevents Ready. Static `tools.catalog` is capability description only. A direct PersonaStack initialize/tools-list handshake runs only after native effective access succeeds.

Assigned dispatch derives a separate helper-owned key from the exact API conversation and issued MCP namespace within the selected agent and binding. Missing conversation IDs use the existing assignment scope. The same no-model create/discover/effective checks precede the `agent` call. Submission carries that exact session key and the native `expectedExistingSessionId` plus lifecycle revision when supplied. This native admission fence prevents dispatch into a reset session. It does not promise atomic tool-policy snapshots. Native transcript continuity does not replace the API's durable conversation or composed-prompt authority.
