# PersonaStack for macOS specification

## Purpose

PersonaStack for macOS presents a selected PersonaStack web surface in a dedicated native macOS application window.

## Authority

- The canonical public source repository is `https://github.com/personastack/macos`. Its `.github/workflows/release.yml` owns native app builds and public source releases.
- `my.personastack.ai` owns the hosted browser experience, cookies, public OAuth callbacks, and browser-facing composition.
- `personastack-api` owns identity, authorization, and product state.
- WebKit retains the persistent HttpOnly login cookie. The main native host checks the hosted session bootstrap hourly, after wake, on application activation and after an authenticated page loads. Requests stay on the selected app origin and never run on login, logout or foreign OAuth documents. One check runs at a time. Server switching retires the old timer, observers and pending check. API hydration renews the same live session before expiry. Temporary network or auth-store failures preserve the cookie for the next check. Explicit logout, revocation and expired sessions still require sign-in. Native code stores no human bearer or refresh token.
- This client owns the macOS application bundle, WebKit configuration, native window behavior, local harness configuration through each CLI plugin manager, local Desktop Control executor and Cua lifecycle, per-user machine credential custody, authenticated outbound gateway connection, and installer packaging. It does not gain a second human login, workspace/persona authorization, integration/configuration store, or general product-state authority. The API is authoritative for device enrollment, selected configuration, current grants, and revocation. The gateway routes only currently authorized, finite requests to this installation.

## Version 0.1.0 behavior

- Start at the App URL in the saved three-service profile when present. Otherwise use the valid packaged `PersonaStackDefaultURL`; the one public installer defaults to `https://my.personastack.ai/user/personas`. `scripts/package-macos.sh` writes the release default through `PERSONASTACK_DEFAULT_URL`. An absent or invalid packaged value falls back to `http://127.0.0.1:8080/user/personas`.
- Accept `--personastack-url <http-or-https-url>` at startup for WebKit diagnostics. A custom diagnostic URL does not grant Gateway or MCP trust. The user must enter and save all three URLs through native Server Settings before native service credentials are used.
- Keep same-origin navigation in the app. Native bridges accept only registered main views at the exact active App origin, including scheme and port.
- Persist site data in the app's default WebKit data store.
- Keep navigation at the selected App origin in the app. Open user-activated links to other origins in the default browser.
- Native external launches accept only HTTP, HTTPS and mailto links. Web navigation cannot launch local files or arbitrary macOS URL handlers. Reject embedded URL credentials in external and Google OAuth destinations.
- Keep `https://accounts.google.com` OAuth popups in a native child window so Google Sign-In can return to the embedded app.
- Allow automated top-level redirects to preserve existing OAuth callback flows.
- Download non-displayable responses to the user's Downloads directory.
- Honor explicit download attributes for the selected origin and its blob URLs in main and floating chat windows. Preserve existing files by choosing a bounded, collision-free filename in Downloads.
- HTML file inputs in the main window and pop-outs open a native file picker attached to the requesting window. Honor the input's multiple-selection and directory-selection options. Cancel returns no files. Hosted image validation, cropping, uploads, and drag-and-drop remain owned by the web app.
- Expose no native JavaScript bridge, local API, credentials, or direct PersonaStack service connection.

## Native server settings

- The one public macOS installer defaults to `https://my.personastack.ai/user/personas`. Users can open **Server Settings…** from the menu bar or app menu, or press Command-Option-Shift-U.
- Store one complete App, Agent Gateway, and MCP base-URL record in local `UserDefaults`. The record contains no credentials. The production and LAN endpoint sets are predefined. A custom diagnostic URL never inherits production Gateway or MCP trust.
- Accept HTTP or HTTPS origins with optional trailing slash, non-default ports, IPv4, DNS names, and bracketed IPv6. Reject credentials, query strings, fragments, and non-root paths. HTTP traffic is unencrypted. HTTPS keeps normal certificate validation.
- `NSAllowsArbitraryLoads` is enabled because each operator-selected host is not known at package time and both WebKit and native URLSession must accept HTTP. This disables ATS policy for the app's network requests, including minimum TLS and forward-secrecy checks. HTTPS certificate trust evaluation remains enabled. Prefer HTTPS except for a controlled network that needs HTTP.
- A diagnostic `--personastack-url` remains the actual WebKit page URL while native Gateway/MCP features stay unavailable until the complete profile is saved. A corrupt saved profile loads only the local development fallback while Server Settings reports the corruption and permits repair.
- A saved record selects the main `/user/personas` page, the WebSocket Gateway path `/v1/desktop-control/ws`, and MCP `/v1/mcp`. An empty saved state uses the packaged default. Corrupt saved state keeps native settings available and uses the local development fallback until repaired.
- Save validates all three fields before it starts a switch. Switching fences Desktop Control, waits for any managed local harness file installation, invalidates old page replies and pop-outs, retires the old native bridge registrations, persists the record, and creates a fresh WebView at the selected App URL. It does not copy cookies or credentials across origins, revoke an old environment's enrollment, or retarget a local CLI installation.
- Native enrollment credentials and Desktop Control relay preferences are scoped to the full normalized three-URL profile, including when profiles share an App origin. Gateway and MCP trust must match the selected derived endpoints, including scheme and port. A new profile starts with remote control disabled.
- Native authenticated enrollment and Gateway requests reject redirects. Before adding a connection MCP entry, the app makes an unauthenticated `HEAD` request to the exact selected MCP endpoint and rejects a redirect from that preflight request. This preflight does not control redirect behavior for later authenticated requests made by Codex or Claude Code; those clients own their HTTP redirect behavior. Normal HTTPS certificate validation remains enabled.
- The website, API, and native service deployments keep their existing ownership. No server discovery API, second installer, LAN download artifact, or website environment selector is added.

## Automatic updates

- DMG and Homebrew builds use the same Sparkle 2 updater and signed appcast at `https://raw.githubusercontent.com/personastack/homebrew-tap/main/appcast.xml`. Release bundles pin the public Ed25519 key, require signed feeds, verify archives before extraction, disable anonymous profiling and release-note JavaScript, and keep signed-feed failures from expiring.
- Sparkle owns daily update checks, downloads, verification, staging, replacement, and relaunch. Its automatic download preference is the only stored copy of that preference. It defaults off. Enabling it permits background download and installation on normal quit, never a forced restart.
- The native app menu and menu-bar dropdown expose **Check for Updates…** and the automatic-download setting. Update checks start only after application launch and only when the packaged public key and fixed HTTPS feed are valid.
- Background update discovery suppresses Sparkle's scheduled alert and shows a once-per-version in-app toast when the main window is visible or a native notification when it is not. The user can reopen the existing Sparkle confirmation from either reminder. Automatic downloads show their background state without offering an action that starts a competing update check. If Sparkle falls back to scheduled UI for authorization or another required user action, PersonaStack switches to **Continue Update…** and reopens the existing session. Information-only updates remain on a **View Update Information…** path. A single app-lifetime notification delegate routes download and restart actions while preserving concern notifications. Denying notification permission leaves menu actions available.
- Sparkle's progress driver remains visible during download and preparation. The menu projects checking, download percentage, extraction percentage, and ready state. Restart Now uses Sparkle's immediate-install relaunch handler for prepared automatic updates. Manual update confirmation uses Sparkle's install choice. Both paths run normal app termination so Desktop Control shutdown runs. Foreground update restarts reopen the main window and resume the saved Desktop Control relay. A success status appears only after the target bundle version launches.
- When the bundle is on a read-only volume or under App Translocation, PersonaStack does not initialize Sparkle. It performs no update checks, downloads, or install-on-quit attempts. The Updates menu explains how to move PersonaStack into Applications. The saved automatic-download preference remains unchanged and resumes when the user opens the Applications copy. Success remains version-verified, so a failed replacement is not reported as complete.
- Choosing **Skip This Version** in Sparkle clears PersonaStack's matching offer, ready action, notification, and restart metadata. Dismissing the installing-stage confirmation keeps the prepared update ready for ordinary quit or a later restart.
- Release packaging requires a stable numeric `major.minor.patch` version and writes the same value to `CFBundleVersion` and `CFBundleShortVersionString`. The package embeds Sparkle's universal framework and helpers. Release automation publishes the immutable DMG and versioned tap artifact before regenerating and publishing the signed appcast.
- Each release commits authored Markdown in `release-notes/<version>.md` before tagging. The source and tap GitHub Releases use that body. Sparkle embeds the same Markdown in its signed appcast. Preflight rejects missing, mismatched-version, and link-only notes. Appcast validation requires the embedded body to match the authored file.
- The Homebrew cask runs `Install PersonaStack.pkg` and enables `auto_updates`. Sparkle updates use `sparkle:installationType="package"` so the app and privileged components update together. Package updates require administrator approval. The feed is rendered from the authored notes and immutable archive, signed with `sign_update`, and validated against the same Homebrew package. Uninstall removes the private policy branch before removing its files. The pre-write readback must match the full current policy. Post-write readback ignores only the authd-managed modified timestamp and must preserve every authorization field and manual fallback order. Private rights and the baseline receipt are removed only after that readback succeeds. A conflicting live policy aborts uninstall for operator review. Previous app versions without Sparkle require one normal Homebrew or DMG update to bootstrap the updater.
- App replacement preserves the default WebKit data store, local user preferences, native credential files, and normal Desktop Control startup. It does not replay in-memory tasks or drafts.

## Desktop Control relay

PersonaStack forwards authorized GUI operations to a standalone official Cua Driver installation. CUA owns its daemon, login service, local policy, updates, and OS permission identity. PersonaStack owns the authenticated outbound cloud connection and its own CUA sessions. The app never requests Accessibility, screen capture, Apple Events, Full Disk Access, or folder/volume grants for Desktop Control. Chat microphone, notification, selected-server local-network, and harness behavior keep their own permission boundaries.

### Installation and setup

- **Set Up CUA…** opens one native window with Install CUA, Complete CUA Setup, and Connect PersonaStack. An explicit Install CUA action downloads the pinned official signed app when absent. A compatible existing installation is reused. CuaDriver.app lives in `/Applications` and its upstream login agent lives outside PersonaStack storage. An incompatible existing installation is reported without replacement or downgrade.
- Pin release 0.29.1, bundle `com.trycua.driver`, team `YCK386LBJ7`, archive/executable hashes, and the reviewed schemas. Validate the live socket peer's OS identity and code signature against the installation. A filename, PID file, or executable on disk alone cannot authorize the peer.
- The daemon runs standalone `serve` under `com.trycua.cua-driver`. No PersonaStack host-attribution environment or parent-liveness pipe is used. The MCP client uses the pinned CLI's `--embedded` transport guard solely to prevent automatic daemon launch. It does not make the standalone daemon embedded.
- Explicit local setup establishes the upstream login service if missing and invokes CUA's supported permission-grant command. CUA and macOS own all consent prompts. PersonaStack does not emulate a CUA settings application or click system approvals. Fresh service installation opts out of CUA telemetry. Existing upstream configuration is preserved.
- Normal app launch, page reads, status polling, cloud calls, and reconnects never install, start, restart, or reconfigure CUA. Passive checks use the existing socket and nonprompting permission queries. Report absent, stopped, incompatible, or setup-required CUA with a local next action. Connection reachability alone does not establish permission readiness.
- The exact-origin, main-frame setup bridge admits finite typed actions only. The canonical action is `cua_setup` with open, repair, completed, and failed phases. Existing deployed hosted pages' `permissions` wire name enters that same CUA setup path. Both version acknowledgments identify this single implementation. The deprecated `native_executor_ready` reply mirrors CUA readiness for deployed-client decoding only and grants no native execution capability.
- Scope, generation, cancellation, installation identity, and current configuration checks fence setup completion and enrollment. Preparing CUA does not enroll the machine or resume a paused relay. A browser-supplied ready flag, installation ID, path, command, or endpoint is never authority.

### Execution and lifecycle

- API owns enrollment, revocable machine credentials, configuration, persona bindings, runtime target, and revocation. Native credentials retain their current private per-profile storage. One installation reserves one account and one integration configuration across workspaces. Disabled configurations retain that reservation.
- The existing outbound gateway connection carries reviewed commands. Preserve configuration/persona/workspace/generation checks, request deadlines, bounded JSON/media results, and the exclusive PersonaStack lease. No inbound network listener is added.
- macOS exposes only the reviewed CUA tool subset and existing lease/status wrappers. Native filesystem and shell execution are absent. Do not emulate removed operations by typing commands into Terminal. Linux contracts are owned separately and remain unchanged.
- Reject arbitrary tool names, unknown fields, caller-selected sessions, and cloud attempts to install, configure, grant permissions, or manage upstream service/session lifecycle. For app-only upgrades, accept the deployed MCP browser_prepare `confirm: true` wire alias and remove it before upstream validation. The legacy confirm-only request means a new isolated browser with launch allowed. CUA still owns consent and policy. Each PersonaStack lease gets a random CUA session distinct from its bearer token. Internal session termination remains available to the relay.
- Browser operations use pinned upstream schemas and CUA's own local policy. There is no PersonaStack browser consent window, Automation request, page adapter, local recording directory manager, or trajectory executor.
- End, expiry, revocation, pause, disconnect, and quit fence new commands before ending only PersonaStack's upstream session. Require confirmed session termination before admitting a new owner. Unconfirmed cleanup retains an unavailable fence. Never kill CUA or another client's session to finish cleanup.
- CUA remains installed and running after PersonaStack quits or is removed. Removing the cloud configuration ends PersonaStack access only. PersonaStack's cloud relay still requires its app to run.
- Never replay a timed-out or uncertain mutating operation. Preserve finite upstream errors and bounded diagnostics without logging screenshots, clipboard, URLs, paths, command content, credentials, or free-form upstream failure data.
- Lock observations remain diagnostic. CUA determines operation availability. Sleep and inactive-login-session events fence local work. There is no PersonaStack screen-unlock, privacy overlay, privileged control supervisor, or keep-awake subsystem. A running LaunchAgent does not promise GUI control while locked, sleeping, before login, or after FileVault restart.
- The retired locked-control utility remains solely for guarded removal of an existing installation. Preserve its authorization-policy baseline checks and unrelated policy entries. New packages do not install it. Never remove its plugin before successfully restoring the owned policy change.

### Presentation and app lifecycle

- The menu shows CUA readiness separately from the PersonaStack connection. **Set Up CUA…**, **Check CUA Connection**, **Pause/Resume PersonaStack Control**, **Stop PersonaStack Control**, and **Disconnect This Mac…** make ownership explicit. CUA service stop/uninstall is not a PersonaStack menu action.
- Active leases show bounded API-projected persona/workspace labels and an operation category. Missing labels use a generic authorized-persona label. Display names never authorize execution. Menu polling defers during native menu tracking and publishes only changed snapshots.
- **Check CUA Connection** opens Diagnostics immediately with progress and a persistent success or actionable failure result. It works before cloud enrollment and checks only PersonaStack's idle CUA client. It does not resume control or stop CUA. Diagnostics show the last CUA check time and a finite, safe failure reason separately from cloud connectivity.
- Remote status requests refresh passive CUA readiness rather than reporting cached success. Failed command prechecks publish the existing finite readiness state immediately. Completed heartbeat health transitions publish immediately without waiting for the next presence interval. A broken or stale client is replaced on a later health check only after owned-session cleanup succeeds; remote actions are never replayed and CUA itself is never restarted.
- Diagnostics read cached CUA permission status, connection state, versions, session observations, and PersonaStack cleanup state. Opening diagnostics never repairs, installs, requests permissions, or uploads a report. No native file/process executor is presented.
- PersonaStack's existing crash-recovery login agent supervises PersonaStack only. It respects intentional Quit, disabled login intent, selected server, updater handoff, and bounded restart attempts. It owns no CUA service or locked-control endpoint. Its headless process must not initialize NSApplication or claim the GUI LaunchServices identity.
- Main-window navigation failure provides Retry through the retained WebView owner. Stale callbacks cannot overwrite newer navigation. Web failure does not stop the relay.
- Menu/Dock Quit and Sparkle share the existing termination delegate. Asynchronous cleanup runs on the normal run loop before one fresh termination request. The bounded quit deadline remains. Harness processes retain their independent owner. Command-Q changes window presentation rather than terminating the relay.

### Validation

Use in-process installer/service/transport fakes for passive-versus-explicit setup, same-scope completion, cancellation, denial, stale generations, lease revocation, independent CUA lifecycle, and unknown outcomes. Source checks do not establish actual macOS permission attribution. Installed acceptance separately verifies the signed CUA identity, user setup, screenshot/input forwarding, relaunch without prompts, login-service persistence, and CUA survival after PersonaStack removal. Locked/sleeping/closed-lid behavior requires separate upstream qualification and is never inferred from socket reachability.
