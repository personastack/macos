# Managed local cluster qualification inputs

This package owns one private managed Kubernetes runtime through the existing helper. It supplies verified artifacts, the finite ARM64 bootstrap inventory, VZ/K3s/storage configuration, native ownership custody, and bounded installation/lifecycle operations. Source wiring remains behind the signed native acceptance gate. It does not issue cloud credentials or project API readiness.

`PinnedDescriptor` records Lima 2.2.1 for Darwin ARM64, Ubuntu 24.04 release-20260926 for Linux ARM64, K3s 1.37.1+k3s1, its ARM64 airgap archive, and the upstream local-path-provisioner 0.0.37 manifest. The Ubuntu disk contains kernel package `linux-image-6.8.0-142-generic` version `6.8.0-142.142`. Kernel identity follows that disk's digest. There is no moving guest-image fallback.

Artifact hashes and lengths were checked against upstream release metadata and checksum files on 2026-11-04. The provisioner manifest hash was calculated from the exact tagged raw file. The exact upstream manifest is embedded and verified before transformation. Do not apply it unmodified. `VerifyArtifact` verifies exact byte length and SHA-256 without executing or extracting input.

`BootstrapImages` records all eight image indexes and their ARM64 manifest/config digests inside the verified K3s archive. `ArchiveReference`, `CacheTag`, and `CacheReference` identify the imported source, cache-local tag, and immutable cache-local index. The native installer stages the verified archive under K3s' private image directory before starting K3s. Normal K3s import adds those aliases using `system-default-registry`. `localhost:5000` is an identity in containerd's cache. No registry service is installed. This inventory falls under the explicit checksum-pinned ARM64 K3s-bootstrap exception in `docs/ARCHITECTURE.md`. It does not change application-worker image ownership.

`Bootstrap` emits the tested K3s configuration and full upstream provisioner resource set. K3s owns built-in CoreDNS and metrics-server. Traefik, ServiceLB, and packaged local-storage are disabled. DNS, CNI, kube-proxy, network policy, and node leases remain enabled. The explicit cache-local pause digest and dead Docker Hub mirror endpoint prevent registry fallback. Deployment and helper Pod references use the exact audited cache-local digest with `imagePullPolicy: Never`.

The provisioner renderer uses YAML nodes because the upstream Kubernetes resource template is its authoritative third-party schema. It changes only known image/pull-policy paths, the default StorageClass name/annotations/binding mode, and shared-filesystem configuration. It preserves upstream RBAC, probes, PVC setup/teardown scripts, and helper Pod structure. The sole default class uses hostPath PVs and shared-filesystem mode over guest-local ext4 with an empty `nodePathMap`. `Immediate` binding adds no consumer gate. PVC capacity is not an enforced quota. Single-node use is mandatory. The preparation script checks ext4 without formatting or deleting a disk.

`RenderVMConfig` accepts paths only from the trusted native artifact owner. It emits one pinned local guest image and the fixed VZ isolation configuration. The caller owns private directory permissions, symlink rejection, verified artifact custody, a sanitized child environment, and fixed executable invocation. Set the returned `LimaHome` as `LIMA_HOME` and use the fixed `InstanceName` (`p`). The factory uses `~/Library/Application Support/PSK8s`. Its short private names fit the tested 32-character username path. Oversized custom homes fail closed. User `~/.lima` and `~/.kube` paths, remote image URLs, malformed paths, and oversized Unix-socket paths are rejected. Host mounts, service forwards, SSH-agent/X11 forwarding, host kubeconfig copying, Rosetta, nested virtualization, package upgrades, and Lima's second containerd are disabled. Private guest control may use Lima's loopback SSH fallback when vsock SSH is unavailable. `guestIPMustBeZero: false` explicitly covers every service bind address.

The macOS 14 app baseline exceeds Lima VZ's macOS 13.5 minimum. The exact downloaded upstream launcher started the pinned guest on macOS 27. It is ad hoc signed. PersonaStack Developer ID/hardened-runtime distribution and macOS 14 execution remain unqualified.

The private 2026-11-04 fixture proved K3s startup, normal built-in CoreDNS/metrics-server, concurrent UID1000/65532 RWX writes, native subpaths, retained data after Pod replacement and VM restart, real Service/DNS/NetworkPolicy behavior, and bounded cluster-agent exec/attach/copy/Pod/Node/Lease operations. Two CPUs, two GiB memory, and an eight-GiB virtual disk sufficed for that synthetic fixture. These are configuration lower bounds, not a full-worker default or host availability promise. The complete application-worker/harness/browser/BuildKit dependency family, SQLite/harness reopen, signed helper lifecycle, OS permissions, sleep/wake, and full resource budgets still need their owning acceptance evidence.

## Concrete native workflow

`NewRuntime` accepts native-owned root/bundle paths and explicit resources. Construction does not create directories, download software, or start a VM. `Enabled` reads private native intent without executing a child. A passive absent-root `Probe` also creates nothing. The factory does not accept page paths, URLs, commands, tokens, or image overrides.

`Install` reserves the native account/workspace owner before cloud enrollment. It downloads only the pinned guest, K3s binary, and airgap archive. Verified cached files are reused. The downloader disables inherited proxies, permits only bounded official HTTPS redirects, enforces exact bytes and SHA-256, and retains interrupted data without trusting it. Lima is extracted and sealed by the existing app packager. Runtime execution has no downloaded or Homebrew Lima fallback.

Before executing Lima, the runtime verifies the outer app and Lima launcher against the fixed identifiers, team, and persistent release certificate. It requires hardened runtime, the sole virtualization entitlement, a sealed source-pinned manifest, and hashes for the launcher, guest agent, license, and version. Signed resources and native data are opened without following symlinks. Native data directories must belong to this UID and remain private. File writes reject hard links and non-regular files before truncation. Unsafe custody fails without reset or deletion.

The workflow uses a sanitized environment and fixed absolute executables. K3s and bootstrap files enter the guest over stdin. The guest verifies K3s/archive size and digest before execution. It applies only the source-owned provisioner bootstrap. Node and installed component rollout observations complete installation. No storage canary or persona Pod is created. Trusted native `ApplyManifest` sends the bounded API-owned install response through stdin. It never stores or logs those credentials on the host.

The whole install has a twenty-minute deadline. Downloads have ten-minute budgets. VM start has three minutes. Guest staging/bootstrap has five minutes. Component checks have three minutes. Lifecycle start has five minutes. Stop has forty-five seconds. Command cancellation kills the owned process group and waits for exit. A failed or cancelled start also stops the VM this attempt started. Failure to prove that stop stays a failure. Diagnostics retain at most thirty-two operation/duration/result records. They contain no arguments, child output, manifests, or credentials.

`Stop` clears enabled intent and observes Lima stopped, the captured host-agent PID absent, and no disk handles. It retains the disk. `Shutdown` makes the same observations while preserving enabled intent. Startup `Restore` and scope-free native `Start` use only an existing bootstrapped owner and retained disk. A removed disk never causes fresh installation or cloud enrollment. Missing or changed owner/data produces details guidance. Signed component mismatch produces update-app guidance. Download checksum failure permits a bounded download retry.

Source tests use isolated files, strict process/HTTP fakes, and no live runtime. They cover failure gates, checksum reuse, custody links/FIFOs, retained resume, scope denial, stdin redaction, cancelled-start cleanup, and observed-stop failures. They do not replace signed helper, OS permission, sleep/wake, or actual installer acceptance.

## Native setup task owner

`Manager` holds one asynchronous task slot for install, scoped resume, manifest apply, native stop, machine resume, local removal and explicit blank setup. `Start` returns an attempt snapshot without waiting for installation. Status and cancellation hold only a short snapshot lock. Startup `RestoreLocal` uses the same slot and calls the runtime's persisted enable intent. It has no page-facing operation. The concrete runtime owns its work and child-process shutdown. Cancellation reports `cancelling` until the workflow returns `context.Canceled`. A successful return still reports completion if cancellation raced with success. Cancellation does not promise rollback or prove that a VM has stopped.

The scoped task owner is the native-supplied app origin, account and workspace. Account and workspace IDs are opaque bounded strings. The original document UUID is metadata. A reopened document for the same owner can read progress. It receives no cloud authorization from that observation. Another owner receives only an occupied error. Status accepts an omitted attempt ID to passively discover the same owner's current task. A supplied attempt ID must match. Cancellation always requires the exact current attempt ID. Passive status with no recorded scoped task returns `no_task`. It does not claim that an installation or files are absent. Late progress from an older or completed attempt cannot alter the current snapshot.

Snapshot operation identifies install, resume, stop, apply, remove or new setup. Successful install reports `installed`. Other successful operations report `completed`. These are native outcomes, not API connection or readiness. Failure reason, message and action come from one finite helper table. Raw errors, child output, paths, manifests and credentials never enter snapshots.

Manifest apply requires a typed canonical integration ID and installation-key fingerprint. It also requires the exact current same-owner completed install or scoped resume attempt. A failed apply can retry with the same retained native custody, exact target binding and current attempt ID. A completed apply duplicate returns the completed snapshot without mutation. The manager copies bounded UTF-8 manifest bytes for the task and clears that copy after the runtime returns. Stop, machine resume, removal, blank reset and startup restore never supply scoped apply authority.

Scope-free stop is a native machine action. It cancels and joins any current task before calling the runtime's verified stop owner. Scope-free resume restores only retained machine-owned state through `Runtime.Start` with an empty scope. Neither operation returns a private task ID, owner or name. Active machine tasks return generic busy to scoped status. Terminal machine tasks permit passive `no_task` observation.

`RuntimeStatus` projects local installation, running, Kubernetes availability, persisted enabled intent and active-task booleans. It does not project API readiness. While a task is active, cached observation remains fenced by `installer_active`. Stop is proven only when no operation is active, native running and enabled intent are false, and no finite failure reason remains. A failed stop retains its guidance until verified stop or completed removal. `RetainForBackgroundStop` rechecks task identity after native observation. It quiesces new task admission under the same lock before allowing helper unregister. Active, enabled, running or unverified state keeps the helper. The finite `local_data_removed` reason is informational and permits stopped proof.

The private control operations are `local_cluster_start`, `local_cluster_status`, `local_cluster_cancel`, `local_cluster_runtime_status`, `local_cluster_runtime_stop`, `local_cluster_runtime_resume`, `local_cluster_apply`, `local_cluster_binding`, `local_cluster_remove` and `local_cluster_new_setup`. Their dispatcher bypasses the existing long connection-operation lock. The current socket checks the peer UID. It does not authenticate each request as coming from a signed app. The native Swift owner must validate the current authenticated scope and human permission. Scope strings do not authenticate a caller. An uninitialized manager returns `runtime_unsupported`. Source task/runtime wiring does not certify a customer feature or close signed native acceptance.

Scoped `local_cluster_binding` returns canonical binding metadata and the removed marker only to the current native owner. It can include a retained previous-removed binding for fresh-key checks. These identities never enter generic machine status or page progress. Apply carries the native binding separately from its transient credential manifest. This mirrors identity for safe local ownership checks. It does not add cloud authority.

Explicit local removal works offline. The generic native menu form provides no scope or target IDs. The runtime derives its existing owner privately from fixed app-owned custody. Removal cancels and joins prior work through the common manager. The runtime owns the initial stop and stopped proof. A tombstoned retry checks remaining PIDs and disk handles without requiring Lima metadata or a second caller stop. FD-anchored deletion rejects filesystem device changes before traversal. The scoped form retains exact owner/binding checks. Both forms share the current task owner. Removal does not imply cloud retirement or wait for it. A removed tombstone prevents automatic recreation.

Explicit new blank setup is a separate action. Only its runtime guard may replace the prior scope after removal and absent VM disks. Pending callbacks belong to the newly provided human scope. Failure keeps the previous reservation. Completion releases the manager's reservation without starting an installer. The runtime retains its previous-binding guard. Native code must establish a new key and target before applying another manifest. Reusing the removed target or fingerprint is forbidden.

Existing private `status` includes `local_cluster_control_version: 1` only when the controller initializes this task owner. Its absence is compatible with older helpers. This advertises private IPC implementation. It does not advertise installation, readiness or a qualified customer feature. Existing check and repair result JSON remains unchanged.

`Runtime.Requirements()` supplies the configured CPU, VM memory, disk budget and exact first-download byte count before setup has effects. The existing private status DTO needed `local_cluster_requirements` because its IPC version and connection rows cannot represent these quantities. The immutable controller metadata appears only in initialized unfiltered status, including external-credential failure status. Check, repair and legacy output keep their existing shape. Initial downloads include the pinned guest, K3s binary and airgap archive. They exclude bundled Lima and later provider images.

The installer requires physical host memory of at least twice the configured VM memory. The provisional eight-GiB VM budget therefore requires sixteen GiB of physical memory. This preserves a host-memory budget. It does not measure available RAM or tune resources. Native consent must show these source values and background behavior before creating an installation key or starting downloads. These internal source notes describe an unreleased path and do not change public documentation.
