# PersonaStack for macOS specification

## Purpose

PersonaStack for macOS presents a selected PersonaStack web surface in a dedicated native macOS application window.

## Authority

- `my.personastack.ai` owns the hosted browser experience, cookies, public OAuth callbacks, and browser-facing composition.
- `personastack-api` owns identity, authorization, and product state.
- This client owns the macOS application bundle, WebKit configuration, native window behavior, local harness configuration through each CLI plugin manager, local Desktop Control executor and Cua lifecycle, per-user machine credential custody, authenticated outbound gateway connection, and installer packaging. It does not gain a second human login, workspace/persona authorization, integration/configuration store, or general product-state authority. The API is authoritative for device enrollment, selected configuration, current grants, and revocation. The gateway routes only currently authorized, finite requests to this installation.

## Version 0.1.0 behavior

- Start at the App URL in the saved three-service profile when present. Otherwise use the valid packaged `PersonaStackDefaultURL`; the one public installer defaults to `https://my.personastack.ai/user/personas`. `scripts/package-macos.sh` writes the release default through `PERSONASTACK_DEFAULT_URL`. An absent or invalid packaged value falls back to `http://127.0.0.1:8080/user/personas`.
- Accept `--personastack-url <http-or-https-url>` at startup for WebKit diagnostics. A custom diagnostic URL does not grant Gateway or MCP trust. The user must enter and save all three URLs through native Server Settings before native service credentials are used.
- Keep same-origin navigation in the app. Native bridges accept only registered main views at the exact active App origin, including scheme and port.
- Persist site data in the app's default WebKit data store.
- Keep navigation at the selected App origin in the app. Open user-activated links to other origins in the default browser.
- Keep `https://accounts.google.com` OAuth popups in a native child window so Google Sign-In can return to the embedded app.
- Allow automated top-level redirects to preserve existing OAuth callback flows.
- Download non-displayable responses to the user's Downloads directory.
- HTML file inputs in the main window and pop-outs open a native file picker attached to the requesting window. Honor the input's multiple-selection and directory-selection options. Cancel returns no files. Hosted image validation, cropping, uploads, and drag-and-drop remain owned by the web app.
- Expose no native JavaScript bridge, local API, credentials, or direct PersonaStack service connection.

## Version 0.1.3 behavior

- Request macOS notification permission when the application opens.
- Accept only the main-frame concern bridge payload `{ "version": "1", "event": "created" }` from the exact active App origin.
- Post a generic native notification when a new concern arrives while the app is running.
- Do not pass concern text, concern IDs, workspace IDs, user IDs, credentials, or other product data through the bridge.

## Floating persona chat

- The hosted page detects the reply-capable `personastackChat` handler. Its existing Chat buttons open one ordinary native window per persona instead of the browser dock.
- Each window loads `/user/personas/chat/desktop-popout?persona_id=…` at the configured app origin. It shares the default WebKit data store. Native code never reads transcripts or calls chat APIs.
- A native, draggable dark title bar uses the standard macOS close and minimize buttons and a right-aligned Pin button. The native zoom button stays hidden. The hosted card meets the matching title bar with a square, borderless top edge. A matching fill behind its upper content removes transparent corner cutouts. A public layer mask keeps the lower chat-card corners transparent. Collapsing hides the bar, Pin button, and native buttons and resizes the same web view to a 72-point window containing a 64-point avatar.
- The native minimize button miniaturizes to the Dock. The sole Pin button sits in the top-right title bar and uses the hosted chat action's 28-point circular border and 14-point outlined pin. It toggles `.normal` and `.floating` for that window. The native chat web view hides hosted pin controls even on older hosted pages. Avatar click collapses or expands. Avatar/header drag also moves the window. Expansion preserves the expanded size at the avatar's current location and clamps to the screen.
- The native close button and Cmd-W use the hosted API-backed close flow. Failed closes keep the chat visible. Navigation errors, denied loads, login/logout navigation, and changed hosted presentation scope dispose stale windows. Same-scope main-page navigation preserves them.
- Main bridge messages have version `1`, action `sync` with an opaque hosted storage `scope`, or `open_persona_chat` with that scope and `persona_id`. Scope is an in-memory invalidation key, never an authorization source.
- Popout bridge messages use version `1` and only `minimize`, `close`, `collapse`, `expand`, `pin`, or `drag` with finite bounded `dx`/`dy` numbers. Reject extra keys, unregistered web views, child frames, and origins other than the configured app origin.
- Window geometry, pinning, and the persona-window map are ephemeral. No launch restoration, all-Spaces mode, native message storage, new authentication flow, or independent stream is added.
- Run focused native checks with `swift test --disable-xctest`. Tests use Swift Testing and in-process AppKit windows without network loads.
- Explicit hosted/native acceptance uses the sibling web repository: build its TypeScript assets, then run `node scripts/desktop-chat-fixture.mjs`. Set `PERSONASTACK_CHAT_FIXTURE_URL` to its printed loopback URL and run `swift test --disable-xctest --filter HostedChatSmokeTests` in this repository. The fixture uses fake messages. This lane is skipped by ordinary tests and never contacts the PersonaStack API.

## Stack pop-outs

- Only the desktop app exposes pop-out controls on Stack Settings. A strict main-frame `personastackStack` bridge accepts version `1` `open_stack_view` messages with one validated `stack_id` and either `graph` or `stream` view.
- Each view and stack pair has at most one ordinary, resizable, Dock-miniaturizable, visually borderless native window. It loads `/user/stacks/desktop-popout?stack_id=…&view=…` through the shared WebKit data store. Native code never reads stack content or calls PersonaStack APIs.
- The graph page and native canvas are transparent. The graph-only WebKit view disables its default opaque page fill so the OS remains visible between graph elements. It renders only the existing shared graph personas, integration circles, connection lines, and motion. The stream keeps its existing hosted card surface and stack-name heading against an opaque, edge-to-edge canvas.
- Stream windows hide the standard titlebar controls and use a narrow draggable native strip with a custom close button at the top-right. Do not add a window menu bar.
- Windows are ephemeral and close on login/logout invalidation, failed or denied hosted navigation, WebKit termination, or normal window close. They are not restored across app launches.

## Persona activity pop-out

- Open one ordinary native window per persona at `/user/personas/activity/desktop-popout?persona_id=…` in the shared WebKit data store. The authenticated hosted page subscribes to the existing authorized persona console stream and uses the same transcript renderer as Persona Settings.
- Keep the native titlebar controls hidden. Overlay the draggable native close control on the hosted Live Console title row, with no separate strip, title, or menu bar.
- Native code handles window presentation only. It never reads or relays persona activity data. Persona authorization and stream access remain owned by the hosted web/API path.
- Persona activity windows are ephemeral and close on session invalidation, failed or denied hosted navigation, WebKit termination, or normal window close.

## Native server settings

- The one public macOS installer defaults to `https://my.personastack.ai/user/personas`. Users can open **Server Settings…** from the menu bar or app menu, or press Command-Option-Shift-U.
- Store one complete App, Agent Gateway, and MCP base-URL record in local `UserDefaults`. The record contains no credentials. The production and LAN endpoint sets are predefined. A custom diagnostic URL never inherits production Gateway or MCP trust.
- Accept HTTP or HTTPS origins with optional trailing slash, non-default ports, IPv4, DNS names, and bracketed IPv6. Reject credentials, query strings, fragments, and non-root paths. HTTP traffic is unencrypted. HTTPS keeps normal certificate validation.
- `NSAllowsArbitraryLoads` is enabled because each operator-selected host is not known at package time and both WebKit and native URLSession must accept HTTP. This disables ATS policy for the app's network requests, including minimum TLS and forward-secrecy checks. HTTPS certificate trust evaluation remains enabled. Prefer HTTPS except for a controlled network that needs HTTP.
- A diagnostic `--personastack-url` remains the actual WebKit page URL while native Gateway/MCP features stay unavailable until the complete profile is saved. A corrupt saved profile loads only the local development fallback while Server Settings reports the corruption and permits repair.
- A saved record selects the main `/user/personas` page, the WebSocket Gateway path `/v1/desktop-control/ws`, and MCP `/v1/mcp`. An empty saved state uses the packaged default. Corrupt saved state keeps native settings available and uses the local development fallback until repaired.
- Save validates all three fields before it starts a switch. Switching fences Desktop Control, waits for any managed local harness file installation, invalidates old page replies and pop-outs, retires the old native bridge registrations, persists the record, and creates a fresh WebView at the selected App URL. It does not copy cookies or credentials across origins, revoke an old environment's enrollment, or retarget a local CLI installation.
- Keychain enrollment credentials and Desktop Control relay preferences are scoped to the full normalized three-URL profile, including when profiles share an App origin. Gateway and MCP trust must match the selected derived endpoints, including scheme and port. A new profile starts with remote control disabled.
- Native authenticated enrollment and Gateway requests reject redirects. Before writing a bearer-bearing local MCP plugin, the app makes an unauthenticated `HEAD` request to the exact selected MCP endpoint and rejects a redirect from that preflight request. This preflight does not control redirect behavior for later authenticated requests made by Codex or Claude Code; those clients own their HTTP redirect behavior. Normal HTTPS certificate validation remains enabled.
- The website, API, and native service deployments keep their existing ownership. No server discovery API, second installer, LAN download artifact, or website environment selector is added.

## Automatic updates

- DMG and Homebrew builds use the same Sparkle 2 updater and signed appcast at `https://raw.githubusercontent.com/personastack/homebrew-tap/main/appcast.xml`. Release bundles pin the public Ed25519 key, require signed feeds, verify archives before extraction, disable anonymous profiling and release-note JavaScript, and keep signed-feed failures from expiring.
- Sparkle owns daily update checks, downloads, verification, staging, replacement, and relaunch. Its automatic download preference is the only stored copy of that preference. It defaults off. Enabling it permits background download and installation on normal quit, never a forced restart.
- The native app menu and menu-bar dropdown expose **Check for Updates…** and the automatic-download setting. Update checks start only after application launch and only when the packaged public key and fixed HTTPS feed are valid.
- Background update discovery suppresses Sparkle's scheduled alert and shows a once-per-version in-app toast when the main window is visible or a native notification when it is not. The user can reopen the existing Sparkle confirmation from either reminder. Automatic downloads show their background state without offering an action that starts a competing update check. If Sparkle falls back to scheduled UI for authorization or another required user action, PersonaStack switches to **Continue Update…** and reopens the existing session. Information-only updates remain on a **View Update Information…** path. A single app-lifetime notification delegate routes download and restart actions while preserving concern notifications. Denying notification permission leaves menu actions available.
- Sparkle's progress driver remains visible during download and preparation. The menu projects checking, download percentage, extraction percentage, and ready state. Restart Now uses Sparkle's immediate-install relaunch handler for prepared automatic updates. Manual update confirmation uses Sparkle's install choice. Both paths run normal app termination so Desktop Control shutdown runs. Foreground update restarts reopen the main window and resume the saved Desktop Control relay. A success status appears only after the target bundle version launches.
- When the bundle is on a read-only volume or under App Translocation, PersonaStack does not initialize Sparkle. It performs no update checks, downloads, or install-on-quit attempts. The Updates menu explains how to move PersonaStack into Applications. The saved automatic-download preference remains unchanged and resumes when the user opens the Applications copy. Success remains version-verified, so a failed replacement is not reported as complete.
- Choosing **Skip This Version** in Sparkle clears PersonaStack's matching offer, ready action, notification, and restart metadata. Dismissing the installing-stage confirmation keeps the prepared update ready for ordinary quit or a later restart.
- Release packaging requires a stable numeric `major.minor.patch` version and writes the same value to `CFBundleVersion` and `CFBundleShortVersionString`. The package embeds Sparkle's universal framework and helpers. Release automation publishes the immutable DMG and versioned tap artifact before regenerating and publishing the signed appcast.
- Each release commits authored Markdown in `release-notes/<version>.md` before tagging. The source and tap GitHub Releases use that body. Sparkle embeds the same Markdown in its signed appcast. Preflight rejects missing, mismatched-version, and link-only notes. Appcast validation requires the embedded body to match the authored file.
- The Homebrew cask enables `auto_updates` beginning with the first updater-enabled release. Previous app versions without Sparkle require one normal Homebrew or DMG update to bootstrap the updater.
- App replacement preserves the default WebKit data store, local user preferences, Keychain services, and normal Desktop Control startup. It does not replay in-memory tasks or drafts.

## Local runs

- Run Local is available only in the native app on Apple silicon and macOS 26 or later. The hosted app and existing chat windows retain macOS 14 support. On the first click, a missing or incompatible runtime opens guided setup. Explicit Install Runtime downloads Apple's signed `container` 1.4.1 package from its fixed release URL, verifies the pinned SHA-256 and size bound, and opens macOS Installer for user approval. Continue rechecks installation before starting the service with recommended kernel installation enabled. An installed but stopped runtime offers Start Runtime. Preparation shows progress, permits only one setup at a time, and fences installation and agent preparation when account scope changes. Cancellation returns an explicit `cancelled: true` prepare reply so the hosted page issues no ticket or error toast. A ready runtime proceeds directly to the working-folder picker. Host-integration instructions remain required for Mac localhost forwarding. Setup never silently installs software, changes packet-filter rules, or disables Private Relay.
- Registered main WebViews expose `personastackLocalRun` with `state`, `prepare`, and `start`. Exact configured origin and main-frame checks are mandatory. Preparation generates a fresh session UUID and private PKCE verifier, returns only its challenge, and asks for a working folder in a native picker. Authenticated web preparation returns an opaque startup ticket. Native redeems that ticket against the configured app origin with its private verifier. Redirects are rejected. Provider credentials, launch files, MCP bearer tokens, and runtime socket secrets never enter WebKit.
- Each click opens a new independent native chat window. Native validates the API-owned persona, workspace, selected MCP endpoint, immutable worker reference, protocol version, file paths/digests/modes, and bundle limits. Image pull and inspection must resolve the approved reference to the same repository's digest with a Linux arm64 variant before launch. No tag fallback is permitted after inspection fails.
- The API owns prompt composition, desktop global instructions, skill snapshots, provider/integration credentials, and Linux startup command. Desktop materializes the complete startup bundle into a private 0700 per-session directory with 0600 files. One read-only directory share supplies a Linux bootstrap that copies those files to the API-owned private destinations before executing the original worker command. Project files are never bootstrap destinations. It does not reconstruct provider configuration or select cloud run placement.
- Apple container runs the approved worker as guest UID/GID 0 because [Apple's virtiofs volume behavior](https://github.com/apple/container/blob/1.4.1/docs/volumes.md) maps the Mac owner's files to guest root with a private Linux home at `/home/persona`, the selected project at `/workspace`, and the Mac filesystem at `/host`. Guest root does not grant Mac root privileges. File sharing follows the container runtime's Mac permissions and TCC grants. Native host commands follow PersonaStack's Mac permissions. Private artifact readability and project writes require exact-runtime Mac acceptance. The desktop Claude bundle sets `IS_SANDBOX=1` for its existing container harness permission mode. Cloud PVCs and cloud harness history are not mounted. Optional API-selected BuildKit companions belong only to this local window. BuildKit receives guest Linux capabilities with no host filesystem shares. Native waits for its private published Unix socket before starting the worker with a socket forward into the guest.
- Mac localhost must be reachable through `host.container.internal`. Startup proves forwarding by reaching a random, content-free response from a temporary native IPv4 loopback listener. DNS registration alone is insufficient because the runtime's packet-filter rule disappears on reboot. A failed probe stops startup and directs the user to the host-integration setup. Container `localhost` remains the Linux guest.
- Messages, cumulative assistant text, commentary, tool lifecycle/output/diffs, turn interrupts, and supported question/approval replies use the worker-owned version 1 newline-JSON protocol over a private published Unix socket. Every frame is scoped to the window UUID. Frames are capped at 1 MiB. Transcript items are keyed by turn and event identity. The native UI shows plain lifecycle states and expandable tool details, preserves reading position, and keeps sensitive question answers out of the transcript.
- `personastack-host` requests use that same authenticated socket and the window's native host executor. They require no gateway enrollment and cannot be submitted by the WebView. Native commands run as the logged-in user through the existing bounded shell executor. Closing the window fences new requests and cancels/reaps its native processes.
- Stop interrupts the current turn, cancels its active native commands, and preserves the local window. Closing the window stops/deletes only its worker and companions, removes the private startup files, and requests API credential revocation. Only a 204 response confirms revocation. A server or network failure leaves a retryable window that says the local agent stopped but credential revocation is unconfirmed. The bundle stays private in memory for that retry. Close awaits an in-flight startup redemption so a late credential retains this cleanup owner. User project files remain. Failed local stop stays visible and retryable. Logout, origin/profile switching, and app quit fence late callbacks and stop the same resources. Normal quit waits for cleanup rather than leaving a detached agent behind.
- Local sessions have no hosted chat-session identity, cloud message routing, remote transcript persistence, or background wake ownership. They do not resume after restart. Logs must never contain startup bundles, credentials, native command contents, or unrestricted worker output. Rich output is kept only in the owning chat window with bounded memory.

## Local persona sessions

- Only registered main application web views expose the reply-capable `personastackLocalSession` bridge. Validate exact configured origin, scheme, port, and main frame. Floating chats and OAuth popups cannot launch sessions.
- Version `1` request messages are `state`, `select_harness`, `prepare`, and `configure`. The `state` reply reports capability version `2` when native Configure is supported. Older version `1` replies identify clients that must be updated before preparation. Reject unknown fields. All messages carry the hosted presentation scope. Preparation checks the installed CLI before returning a native pending UUID. Pending IDs bind persona and harness for five minutes and are consumed once. Scope changes and login/logout invalidate pending work.
- Support only installed Codex CLI and Claude Code. Probe the user's login shell with bounded output and time. Require at least the inspected Codex 0.154.0 or Claude Code 2.1.152 baseline and required plugin-manager commands. Missing or unsupported CLIs require user installation or update. Never run an installer or obtain provider credentials.
- Keep one native harness preference per app origin. `select_harness` persists that preference without preparing or configuring a harness. Never persist bearer tokens or local-harness bundles in preferences. The hosted app remains responsible for the later authenticated configuration-preparation POST. The API owns each independent fixed 365-day credential and its ongoing authorization.
- Validate the typed local-harness bundle, fixed lifetime, selected profile's exact MCP endpoint, artifact digest, aggregate limits, and safe paths before local writes. Production and LAN profiles use their configured MCP endpoints. A custom profile is accepted only after all three service URLs are explicitly selected and saved; its bundle must match that profile's exact MCP endpoint, including scheme, host, and port.
- Private desktop plugin sources live under `~/Library/Application Support/PersonaStack/LocalHarnessPlugins/<harness>/<profile-hash>/<UUID>` with mode 0700. Files use 0600. An ownership manifest and source digest record the active source for that harness profile. Reconfiguration validates the recorded source, registered marketplace, installed plugin identity, and cache permissions before it removes only the recorded PersonaStack plugin and marketplace. Refuse symlink traversal, unmanaged collisions, and modified owned content.
- Each source is a local marketplace with one `personastack-local-<profile-hash>` plugin and `personastack-desktop-<profile-hash>` marketplace. Codex uses `.agents/plugins/marketplace.json`, `.codex-plugin/plugin.json`, and its `mcpServers` manifest shape. Claude Code uses `.claude-plugin/marketplace.json`, `.claude-plugin/plugin.json`, and its direct server-map manifest shape. Both receive a private authenticated MCP entry, the eager `PersonaStack` skill, and namespaced selected-skill snapshots that preserve relative assets and metadata. After install or retry, Desktop makes the verified managed cache owner-only. Path aliases are accepted only when they identify the same source directory. Cache permissions change only after plugin identity and full source contents match.
- Configuration runs only bounded selected-CLI plugin-manager commands with the existing profile directory. It never opens Terminal or starts an interactive CLI harness. It never edits `AGENTS.md`, `CLAUDE.md`, shell profiles, raw CLI configuration, or profile symlinks. Existing CLI auth, profiles, model settings, MCP servers, hooks, and plugins remain user-owned.
- Local-session diagnostics use the `ai.personastack.desktop` OSLog subsystem and `local-session` category. Record only allowlisted action names, fixed stage names, and finite error codes. Never log request bodies, scope, persona/workspace identifiers, pending IDs, bundle fields, bearer credentials, paths, CLI command output, or unrecognized input values. Read recent events with `/usr/bin/log show --last 10m --style compact --predicate 'subsystem == "ai.personastack.desktop" AND category == "local-session"'`.
- This is not a sandbox. Downloaded private skills and persona instructions remain on the Mac. Existing CLI tools and plugins retain their user's trust. Fakes do not prove live CLI authentication or provider/MCP connectivity. Those require separately authorized smoke tests.

## Installer distribution

Each semantic version is a universal macOS disk image with a branded Finder background, a drag arrow, and an Applications shortcut. Users install by dragging `PersonaStack.app` onto `Applications`. A public GitHub release retains the immutable `PersonaStack-<version>-selfsigned.dmg` installer. The app is sealed with one persistent certificate-backed signing identity. It is not Developer ID signed or notarized. The release workflow copies the same DMG into a versioned public `personastack/homebrew-tap` Git tag and updates the `personastack` cask. Homebrew installs it with `brew install --cask personastack/tap/personastack`. Earlier unsigned release artifacts remain immutable.

Light rounded backgrounds keep the native PersonaStack and Applications labels readable against the dark artwork. Finder uses 12-point labels below the 112-point icons without item information.

Packaging requires `PERSONASTACK_CODESIGN_IDENTITY` and `PERSONASTACK_CODESIGN_KEYCHAIN`. The release imports the protected persistent PKCS#12 identity into a temporary job keychain. Its leaf certificate must match the committed public `Resources/ReleaseSigningCertificate.der`. Bundle validation requires sealed Info.plist/resources and the exact certificate-anchored designated requirement for `ai.personastack.desktop`. Ad-hoc and unsigned bundles fail. The release gate signs two differing bundles and proves mutual identity continuity. It rejects a different certificate using the same identifier and rejects changed sealed resources. Signing does not grant OS capabilities. Users must reapprove grants associated with earlier unsigned builds once. The app never resets TCC or reports a capability granted from Settings appearance alone.

## Desktop Control relay

- On the first launch of an installed app copy, register Launch at Login automatically through `SMAppService.mainApp`. Record the attempt once per macOS user. Later launches preserve a user disabling the login item. Existing enabled or approval-pending registrations are not registered again. First launch, checklist setup and the menu action share one registration policy. Both notRegistered and notFound permit a registration attempt. notFound can mean that macOS has never registered the service. It does not prove that the app bundle is missing. Registration always reads back status. A thrown registration error is resolved only if fresh readback is enabled or requiresApproval. Successful return without confirmed status is not reported as enabled. Failed registration or unconfirmed state retains recovery guidance. Resolved current and legacy approval messages clear only after enabled readback. Read-only disk images, App Translocation, and development executables do not consume this first-launch attempt. Registration failures and macOS approval requirements appear in the existing menu error area. The Launch at Login action remains available for a manual retry.
- A desktop-only hosted CTA starts a strict main-frame native setup bridge. It validates the configured app origin and frame, accepts only typed setup/status actions, rejects unknown fields, and never treats a workspace, installation ID, `ready` flag, path, shell command, or URL from JavaScript as authorization.
- Native setup opens one PersonaStack-branded permission checklist. The matched integration page can reopen that same window through the scoped permissions repair phase. Repair presentation performs no enrollment, credential read, runtime repair or configuration replacement. It rejects an active enrollment checklist and preserves that request. The menu's Permissions and Setup action reopens the same window for repair. Every native checklist presentation starts one fresh functional verification pass through Accessibility, Screen Capture, Full Disk Access, Microphone and applicable Local Network rows. Rows remain Checking until their own current check finishes. Later polling reads OS/runtime observations and previously authorized bounded disk/network rechecks. The native window starts with 670 × 740 points of content after its hosting controller is attached. Its content minimum is 560 × 460 points. SwiftUI does not replace the native frame with its intrinsic size. Reopening preserves user resizing. An observed OS grant without functional proof shows Needs verification. Checking is reserved for an unresolved observation or running check. An explicit unresolved result, including failure, missing prerequisite or required restart, remains visible through passive polling until retry, a changed observed grant/identity, or invalidation. A completed proof retains its actual check explanation. Per-row revisions reject passive observations started before Setup and reject explicit results invalidated while running. Opening the native setup or repair window explicitly starts automatic notification authorization, Launch at Login registration, updater configuration and a short-lived sleep-prevention check once per presentation. Passive refresh never runs these actions. Automatic notification setup requests approval only while authorization is undetermined. It preserves denial and disabled alert/sound settings. Registration does not repeat for enabled or approval-pending login items. Automatic setup never opens Settings. An incomplete automatic row offers a manual Retry that may open the relevant Settings. Notifications show a check only when macOS permits both alerts and sounds. Login shows a check only for an enabled SMAppService. Optional work has separate progress. It never blocks required Setup buttons or Finish. Finish cancels remaining automatic work. Cancellation and presentation generations reject late results. Only an explicit Setup button may request new Accessibility, screen capture or microphone grants or open their Settings recovery flow. Each presentation verifies already granted Accessibility and Screen Capture through the existing runtime and tests an already authorized microphone through the current trusted main document. The presentation also runs the fixed protected-folder listing and selected-service HEAD checks without requiring an earlier successful check or stored proof. The window discloses these operations. Accessibility runs first. Optional checks have separate progress and never prevent Finish after required input proof succeeds. Manual Setup skips its pending automatic turn. Conflicting optional Cua work is canceled and drained before manual Cua verification starts. A successful disk or network check may also recheck once when the app becomes active. Ordinary polling never starts input, capture or recording. Failed disk/network rechecks do not repeat until Retry or a new presentation. Content-free functional results expire when their relevant identity, daemon generation, grant or environment changes. Closing or finishing the window cancels the presentation pass, current operation and passive refresh, fences late results and prevents admission of later checks. A new presentation performs fresh checks even after process restart or a changed page document. This release sets up unlocked Desktop Control. The permission list contains Accessibility, Screen Capture, Full Disk Access, Microphone and Local Network. Screen Capture runs the existing actual desktop-capture check, including any supplemental direct-capture approval. Local Network is hidden when the selected cloud services or macOS version do not need it. Full Disk Access replaces separate Desktop, Documents, Downloads and volume approval rows. It remains visible with operation-scoped verification status and does not block current unlocked enrollment. It does not override filesystem ownership, ACLs, SIP, protected data vaults or network-share credentials. Unused Camera, Input Monitoring, Automation, Speech Recognition and System Audio grants are not requested. Locked-screen control remains unavailable and is disclosed above the list. Connection readiness stays in the existing enrollment and completion flow. Finish requires only Accessibility to be functionally verified. Its title includes (Required). Optional Screen Capture, Microphone, Full Disk Access, Local Network and automatic settings do not block Finish. Accessibility completion enables Finish immediately without waiting for optional observations. Finish cancels any pending optional setup and fences its late result. Denied, failed, restricted or unsupported required rows block Finish. Automatic settings remain visible separately and never gate enrollment. Launch at Login registration is owned by first-launch and explicit checklist setup. Enrollment does not register it again or require it to be enabled. Locked-screen control remains unqualified in this implementation. Full Disk Access readiness proves only the disclosed protected-folder operation. The app retains the existing lock denial until signed physical acceptance proves the mechanism.
- Automatic presentation verification and Setup Microphone share the same bounded recording owner. Automatic verification requires an existing authorized OS grant and never invokes the microphone grant request. The current selected secure origin, document and input identity must remain unchanged. The microphone check prefers version `1` of the selected main page's `personastackVoicePermission` hook and its voice-message capture owner. Existing hosted versions without a compatible hook use a bundled native-injected WebKit MediaRecorder check in the same selected-origin document. Native rejects an active or muted WebKit microphone capture. The bundled check requests audio only and requires an actual recorder start, a live audio track and nonempty recording data. It uses a one-second timeslice and stops after the first nonempty chunk. A five-second recording limit starts at the recorder start event. The app must not unlock Keychain, broaden its creator-only access list, replace the credential or change its stable signing identity to suppress that authorization. Page-state access failures expose the existing native Retry action even when relay startup is disabled. Successful access stays in the existing runtime cache and does not itself resume a paused relay. A current validated cache supersedes a concurrent passive Keychain access failure. Successful native authorization clears only the selected profile's exact Keychain access error and preserves unrelated runtime errors. Concurrent authorization requests are refused. Stale reads cannot resume or commit a revoked lifecycle, changed full server profile or changed setup scope. App-launch error publication uses the same captured lifecycle and full profile for paused and unpaused startup. Cancelled or superseded startup cannot overwrite a later recovery result. Login startup must not open the main web window or start duplicate relays. GUI operation requires an awake logged-in user session; locked, asleep, logged-out, and pre-login desktop access is unsupported.
