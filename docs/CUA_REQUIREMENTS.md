# CUA requirements on macOS

This inventory covers embedded CUA Driver **0.29.1**, schema 1, upstream commit `7a8f66ad04e62fccb18cca9965f2964fcaee124e`. The producer-owned `desktop_control_cua` operation exposes all **58** pinned macOS tool names through the existing authenticated control lease. The bundled schema fixture comes from that signed driver's `list-tools` and `describe` output. Tool discovery is not evidence that every variant is usable on every platform. Reaudit the inventory when changing the driver, schema fixture or host policy.

## Guided setup and user actions

PersonaStack installs and verifies the official pinned CUA driver through its native setup/runtime owner. The user does not install a separate CUA app. Required published perception assets are handled in the same attended setup with their disclosed Install review. This integration preserves upstream signatures and supported behavior; it does not maintain an upstream fork.

Full unattended control requires macOS 15 or later. Ordinary chat remains available on the app's older supported systems. The setup window checks the full-control OS requirement before requesting permissions.

One PersonaStack **Continue** starts six ordered stages: Accessibility, screen capture, protected files, browsers, clipboard and Local Network. Screen capture includes the separate direct-capture check. Browsers include Safari Automation, Safari JavaScript and the selected running Chrome/Edge instances. Browser setup is optional. **Skip** cancels the current browser check and advances without recording browser permission approval. Missing browser permissions do not block setup completion or general runtime readiness. Browser-specific tools retain their target-specific permission checks. Successful readbacks advance automatically. Failed required checks remain on the affected stage with one recovery action. Opening the window and passive refresh must not request a grant.

Continue is one app action, not one macOS authorization. An unmanaged Mac can still require separate OS confirmations, System Settings toggles and browser settings. The exact count depends on existing grants and selected browsers. Count these actions separately in signed-app acceptance. The setup also has compact status for Launch at Login, updates, awake-during-work, locked control and visual perception. Requirement revision 3 includes visual perception on supported Apple-silicon Macs. A missing perception component adds one native Install confirmation after its exact review. A healthy installed component adds no install click. This does not add a seventh permission stage. Microphone is absent from this flow.

## Browser consent scope

The native selection approves the **selected running Chrome or Edge process instance**, including its windows, tabs and authenticated profiles. The selected window is an approval anchor. Consent is not limited to one profile or one page. It does not approve future browser processes.

PersonaStack records content-free PID, window, launch time, bundle and code identity in the existing permission receipt. It validates fresh process and window ownership before each protected dispatch. The receipt is bound to the host signing identity, OS, driver and permission requirements revision. Restarting PersonaStack can preserve approval for the same still-running browser instance. Restarting the browser requires local selection again. No raw profile path, page contents or bearer session is stored in that receipt.

Pinned CUA's standard mode accepts `--grant existing-profile` only when starting its daemon. PersonaStack may add that grant only after native consent exists. Every existing-profile call remains subject to fresh target checks. Remote `confirm:true` records browser preparation intent and never creates local consent. Remote `install_extension` is preview-only. Its `confirm:true` is rejected before driver dispatch because installation requires the native artifact review. Attended setup prepares or restarts an owned daemon with the grant and verifies the selected instance’s connection. The consent and connection proof are separate. A warm daemon without the required grant cannot qualify. Setup refuses an active remote lease before changing consent. Unrestricted mode and caller-supplied session or internal authority fields are forbidden.

Upstream `browser_prepare` binds its existing-profile grant to the calling session, transport, target process/window fingerprint, browser product and verified endpoint. Its browser-connection helper searches the selected process's windows and may press the browser-owned debugging connection **Allow** button. The setup disclosure delegates that specific browser handshake as part of the selected-instance consent. PersonaStack does not automate macOS security dialogs. This instance scope replaces the earlier profile-only proposal because the pinned implementation operates across the selected process's windows.

Safari's standard `page.get_text` and `page.query_dom` routes have a pinned upstream targeting defect. The backend selects a document by title substring and falls back to `document 1`. Native ownership and a preflight document count cannot guarantee that this backend reads the requested window. PersonaStack returns `browser_route_unavailable` without dispatching either Safari read, even when attended Automation/JavaScript proof is valid. This is an explicit dependency guard. Exact Safari page reads remain unavailable in this official driver. Upstream modification and forking are outside the requested installation/setup scope. Accessibility observation and input remain available.

The existing Safari setup proof is retained for the operations that need it. Its receipt now binds PID, launch time and signed code identity. Nonprompting Automation preflight repeats process, native window and receipt checks after the query. No remote JavaScript permission probe runs. Browser restart, code change, a revoked grant or a changed receipt requires local verification again. This proof establishes authorization, not the upstream reader's document identity.

Legacy `page` reads use Apple Events and can fall back to title-based window matching even in Chromium. They do not establish exact requested-window fidelity. Native legacy-read admission currently permits only approved Chrome/Edge instances with current Automation and JavaScript evidence. Their documented fallback also does not establish exact requested-window fidelity. Safari reads are explicitly refused pending an upstream fix. The safer typed `browser_*` operations retain their own upstream endpoint binding.

## Full catalog prerequisites and bounded variants

| Tool family or prerequisite | Current contract and remaining qualification |
| --- | --- |
| AX, pointer, keyboard, menus, application and window tools | Use the current control lease, fresh runtime permission checks and supported targeting. Only the host injects the CUA session. No permission probe may prompt remotely. |
| First-class browser tools | Support isolated-new/named preparation and explicitly approved existing Chrome/Edge instances. Exact variant schemas are checked before dispatch. Unsupported browsers and revoked or restarted targets return finite setup errors. |
| Legacy `page` | Pinned standard mode permits `get_text` and `query_dom`. Mutating page actions are refused upstream by default. PersonaStack adapts `insert_text` and `type_keystrokes` through exact typed browser binding, one selected tab, a complete semantic snapshot and one focused editable ref. It uses `browser_type` without replacing existing content. Ambiguous, changed or incomplete targets fail before input. CSS clicks, arbitrary JavaScript and browser preference changes remain unavailable through legacy `page`. PersonaStack does not enable `CUA_DRIVER_ENABLE_LEGACY_PAGE_MUTATIONS` or unrestricted mode. Arbitrary JavaScript and all legacy mutations cannot be faithfully replaced by the typed browser toolset. All 58 names are discoverable, with these variant limitations. The setup installs the official driver and does not fork it to enable unsupported variants. |
| `parse_visual_regions` | The runtime registers this tool and publishes immutable, session-bound capture IDs. It requires the separately installed verified perception extension, model assets and ONNX runtime. The schema's “future capture registry” wording is stale. A missing provider returns an unavailable error. Setup installation, daemon restart and an actual parse remain required before declaring this family ready. |
| `install_extension` | The pinned installer requires a reviewed signed perception catalog configured at daemon launch. `confirm:false` returns the artifact, checksums, destination, trust, license and source plan without installation. `confirm:true` installs after explicit review. The preview is not itself an install or provider qualification. Native setup stages pinned release bytes and delegates inspection and installation to the same upstream CLI. Its status command can run the verified extension health hook. It does not request a screen capture or install. No unsigned catalog or local trust bypass is allowed. |
| Native recording | Native macOS video capture requires macOS 15. Artifacts stay in an owned local directory. The host checks a 256 MiB and 10,000-entry budget periodically, so this is not an instantaneous hard cap. Recording stops on control release/disconnect. Artifacts may contain screenshots, AX state and tool arguments. No automatic upload or deletion guarantee is implied. |
| Replay | The host bounds input to 8 MiB and 1,000 turns. Delays are bounded to 0–10,000 ms. It parses and redispatches approved GUI actions through current lease checks. It rejects nested session/recording/configuration, browser preparation, administrative actions and stale selector references. Cancellation and uncertain transport outcomes abort even when `stop_on_error` is false. |
| Session/configuration tools | The host owns lease/session association. Configuration keys and values have a finite allowlist. Caller-controlled internal fields and foreign session IDs are rejected. |
| `install_ffmpeg` | The native macOS recording backend does not depend on ffmpeg. Platform-specific upstream refusal is not evidence of a missing macOS TCC permission. |
| File and process execution | PersonaStack's native executors retain their current-user authority, filesystem boundaries and process policy. CUA setup cannot grant root, disable SIP or silently approve unrelated application security prompts. |

The official [perception 0.2.1 release](https://github.com/trycua/cua/releases/tag/cua-perception-v0.2.1) publishes a macOS **arm64** archive. It has no Intel macOS archive. Its published install-check reports successful installation, self-test and real parsing with driver 0.29.1. Research verified the small ARM catalog's Ed25519 signature against the public key embedded in the pinned 0.29.1 source. This verifies catalog provenance, not a local install or runtime. The catalog names a 426,075,949-byte archive with SHA-256 `5fbcf59c15fc5cd8beca6ac4aa5533c34359054810aceb12c9e26d7a45e750ab`. The installer resolves that archive beside the catalog and inspects it before returning its full preview. A catalog download alone cannot produce that preview. Intel perception remains an upstream distribution gap. Its component status explicitly reports Not needed with parsing unavailable. It does not fabricate a successful parse or claim identical arm64/Intel capability.

Perception installation belongs in the existing setup's automatic component status rather than a seventh permission stage. The intro discloses the possible 426 MB review download before Continue. Its distinct Install confirmation must be counted in user-action acceptance when the component is absent. A healthy installed artifact skips download/install but still requires current parser proof. Receipt revision 3 retains only scoped historical verification. Cancellation and changed component identity invalidate late or stale proof. The owned-window verifier requires a current capture ID, production parser identity and recognizable fixture text. It ends its setup session before readiness can be recorded. Until the reviewed catalog and installed provider are qualified, full CUA readiness remains incomplete.

## On-demand and conditional access

Microphone permission is requested only after the local user chooses voice input in persona chat. Camera, speech recognition and system-audio capture are not required by the reviewed desktop-control surface. Notifications are not a prerequisite for remote control.

Application Management, access to other applications' protected data, Developer Tools, additional targets' Automation, administrator authentication and network-volume credentials can apply to particular execution tasks. They are not universal grants that can be merged into the CUA setup prompt. A task that needs an unapproved conditional capability must return a finite local-action requirement before attempting a prompt while unattended.

## Validation boundary

In-process fixtures cover permission sequencing, no-prompt observation, scoped receipts, selected-browser identity changes, cancellation, argument validation and lease admission. They do not grant real TCC permissions or establish installed-app prompt attribution. Current implementation evidence and unresolved gates belong in the active implementation plan.

Signed installed-app acceptance must measure actual app actions, OS confirmations and settings actions on fresh and partially granted machines. It must also exercise warm/cold driver startup, selected browser setup, browser restart, host relaunch, revoked permissions, perception installation, locked-session control and LAN denial. No signed acceptance, notarization or release claim follows from a source test or an offscreen window preview.

Current source run `/tmp/personastack-permissions-coherent3.log` passed 859 tests in 54 suites. It includes guided setup, browser attachment, perception, LAN, receipts, admission, owned-session cleanup, typed compatibility typing and native-only extension installation. The two prior executor failures are repaired. Current offscreen previews omit content and provide no valid visual acceptance. The opt-in hidden-window bitmap fixture checks geometry/artifact creation only. Its successful test result cannot certify the rendered UI. Actual native rendering acceptance remains unrun.

Historical evidence from **2026-10-03**, before the full-catalog and guided-flow changes: 116 focused Swift tests passed in 3.4 seconds and resource plists passed lint. Hidden native previews at 670×740, 560×460 and 800×600 showed wrapping and footer placement. Offscreen AppKit omitted button labels. Those observations do not validate the current implementation or live permission dialogs.

The current change spans the native permission owner and the API/MCP/gateway typed operation boundary. It does not move OS permission authority to the API or treat a remote request as local user approval.
